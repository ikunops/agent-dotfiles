# 前端 UI 一致性规范

## 核心立场（先读这段）

> **数值没有绝对标准，一致性才有。**
> 不同项目的字号、控件尺寸差一两号是完全正常的 —— 14px 正文还是 13px 正文，32 还是 36 的控件，都不构成"错"。
> **唯一要保障的是：同一个程序里，A 页面、B 页面、C 页面必须一致。**
> A 页面用尺寸 1、B 页面用尺寸 2，这才是问题。

所以本规范的工作方式是**相对的**：

1. **先清点**：统计项目里各类字面量的真实分布，得出**事实基准**（众数）。
2. **找离群**：只出现一两次的**长尾值** = 嫌疑（往往就是"某个页面独有的怪值"）。
3. **查跨文件分歧**：某个文件的主流值与全局众数不同 = **最该修**的那一类。

判定规则与汇报格式沿用 `ui-acceptance` 的「**横向一致性（众数判定）**」：
**取众数为基准，离群者报 FAIL**，汇报固定为《**N 处中 M 处是 X，这 K 处是 Y**》——不许笼统说"基本一致"。

⚠️ **下面几张数值表只是"新项目起手可选值"**，不是强制标准：
项目还没有自己的刻度时可以用它起步；**一旦项目已有分布，以项目的为准**（用脚本统计出来）。

## 一键审计（这才是主要用法）

```bash
python scripts/audit_ui_consistency.py --root web/src
python scripts/audit_ui_consistency.py --root web/src --out ui-audit.md
python scripts/audit_ui_consistency.py --root web/src --props font,height --max-list 10
```

输出四节：**项目事实基准（众数）→ 长尾离群 → 跨文件分歧 → 怎么改**。

- **长尾离群** = 出现 ≤2 次或 ≤1% 的值（**非众数不等于不一致**：一个项目本来就有多个合法角色档位，如正文/说明/标题）。
- **跨文件分歧**优先修 —— 它直接对应"A 页面一个值、B 页面另一个值"。
- 用 `var(--x)` 的地方**不参与判定**（已 token 化是好事）。
- **数据增长模型不是脚本自动猜出来的**：先按「数据增长与自适应边界」给每个集合定模型，再把常见规模 / 业务峰值 / 硬上限 / 超限策略交给 `ui-acceptance` 和 `frontend-review-squad` 验证；脚本负责发现数字离群，模型负责判断哪些数字本来就不该固定。

## 三个入口

| 场景 | 怎么用 |
|---|---|
| **开发中**（写新页面/组件） | 新值先问：**项目里有没有现成的同类值？** 有就跟随，不要引入新值；确实需要新档位，就同步更新到所有同类位置 |
| **审查 / debug / 优化** | 作为**判定基准**：`frontend-review-squad` Step 2 用它做越界判定（此前只有"统计"没有"基准"）；先跑脚本 |
| **判断要不要抽公共组件** | 见文末「公共组件判定」（阈值 + 三问），接 `debug-and-refactor` Part B |

> 与其它前端 skill 的分工：本文件管**一致性与刻度**；`design-taste-frontend` 管审美方向；
> `workbench-layout` 管工作台布局硬规则；`layout-guardrails` 管溢出与可收缩性；`hallmark` 管反 AI 味。

## 强制原则（按规则性质分三档——禁令不带适用边界会变成教条）

**A 档 · 一致性硬规则**（本规范的核心承诺，违反即 FAIL）：
1. 同一角色控件在同一程序内取值一致；同一区域内的控件高度、圆角、间距一致。
2. 新值允许引入，但必须同步到所有同类位置并登记进档位——"不能自己造"指的是不能造了就丢，不是不能造。

**B 档 · 依赖项目形态的条件规则**（先看项目有没有对应基础设施，再决定怎么执行）：
3. **有 token 体系的项目**：颜色/字号/间距/圆角/阴影/z-index 走 `var(--x)`；**vanilla/无 token 项目**：先建最小 token（CSS 变量），或至少把值集中到一个文件——散落各文件的裸值才是问题，裸值本身不是。
4. **有组件库的项目**：优先组件库与既有封装；**vanilla 项目**：复用既有 CSS 类与页面模式（先搜同类再写）。
5. 数据内联场景（data-URL SVG、第三方嵌入样式）豁免 token 化，但在代码旁注明原因。

**C 档 · 方法性规则**（是方法不是禁令）：
6. 写新 UI 前先搜项目里是否已有相似组件和页面。
7. 新组件通过扩展变体演进；要改基础尺寸 = 修改档位定义并全量同步，不许局部偷偷改。

## 数据增长与自适应边界（先判断，再选布局）

**硬编码不是一个单一缺陷。** 看到固定值、固定份数或写死内容时，先判断它属于哪一类：

| 类型 | 判据 | 正确做法 |
|---|---|---|
| **稳定产品约束** | 值由产品骨架或外部协议决定，运行时不变化 | 可以固定，但收敛为具名常量或语义 token，并注明来源；禁止同一魔数散落在多个组件 |
| **同类内容重复** | 多个实例结构相同、内容不同 | 收敛到数组、配置、API 或 schema 等单一事实源，渲染层遍历生成；禁止模板与逻辑各维护一份 |
| **布局数量假设** | 假定永远只有固定实例数、行数、列数或按钮数 | 改为自适应网格、换行、容器查询、分页、虚拟化或聚合；同时声明真实增长边界 |
| **单条内容可变长** | 实例数稳定，但文本、数值或翻译长度会变化 | 使用 `min-width: 0`、换行、截断 + 完整值入口、容器查询；不要靠增加容器数量解决 |
| **一次性静态内容** | 只有一条固定标题/说明，运行时不增长、不跨环境、不重复 | 保持字面量通常更清楚；不要为了「可配置」制造无意义抽象 |

### 先判数据增长模型

| 模型 | 判据 | 设计含义 |
|---|---|---|
| **固定结构** | 数量由页面/产品结构决定 | 只验缺项、权限态、最长内容和最小可用宽度；不要为假想规模增加分页、搜索或虚拟化 |
| **单条内容可变长** | 实例数稳定，内容长度/语言/精度变化 | 重点验换行、截断、翻译膨胀和数值极值 |
| **增长型同类集合** | 每新增一个业务实体就新增一项 | 必须声明常见规模、业务峰值、硬上限与超限策略；布局不能押注某个「刚好摆得下」的实例数 |

增长型集合不等于都要做复杂组件。**先看用户的任务层级**：若用户先要判断整体，再定位个体，应提供聚合 → 筛选/列表 → 详情；若页面本身就是单实体详情，则不要强加聚合。自适应、分页、虚拟化和聚合都是手段，选用依据是数据规模与任务，不是流行程度。

### 自我检查

- 这个固定值是稳定约束，还是因为只见过当前样本量？
- 同一个值/结构是否在多个位置重复维护？
- 新增一倍、十倍业务实体时，是布局变差、渲染变慢，还是能力完全失效？
- 当前测试数据是否只覆盖「刚好摆得下」的理想数量？
- 固定结构是否被过度设计成搜索、分页、虚拟滚动？

**与渲染层几何的分工（正交边界）**：A/B/C 三档管的是**写法和取值**；
「组件相撞/叠在一起、双圆不同心、图标换行、文字不居中」是**渲染层几何事实**，
归 `ui-acceptance` 第 ③ 层（量矩形：文字级 Range、外圈 w===h、重叠面积），本 skill 查不出它们——
CSS 写得全对也照样能撞。两者关系：③ 层负责「查出撞了」，本 skill 的 B 档负责「解释为什么撞、怎么改」
（碰撞根因绝大多数是 B 档违反：选择器覆盖、容器缺约束、隐含父容器假设），修完回 ③ 层复量。
本项目的完整案例链见实测补遗 1–8。

## 轴系统：先切格子，再落子（构造线法）

一致性不是“把值调成一样”，而是**所有元素服从同一套局部坐标系**。页面不是一个平面，而是逐层切分出来的容器树。

### 1. 递归切分，而不是全页一条主轴

每一层容器只回答三个问题：

1. **这一层沿哪根轴切？** X（横切）或 Y（纵切），一次只选一根主切轴。
2. **切几份、比例多少？** 份数和比例来自内容任务，不来自“看起来差不多”。
3. **缝多宽？** gap / padding / 边界线宽度必须来自 token，不能每层临时发明。

父层只负责给子层一个格子；子层在自己的格子里重新建立局部轴。**父层不替子层决定内部怎么排。** 这就是 BSP / 断头台切分与 CSS Grid 的共同结构。

### 2. 四根轴各管一件事

| 轴 | 管什么 | 典型症状 | 验收量什么 |
|---|---|---|---|
| **X** | 宽度、列、左右边界、水平间距 | 左右边距不一致、列宽失衡、内容挤出 | 左/右边缘、列宽、水平 gap |
| **Y** | 高度、行、基线、垂直节奏 | 卡片高矮不一、字号基线不齐、行距漂移 | 上/下边缘、行高、文字基线 |
| **Z** | 堆叠、浮层、遮挡、焦点顺序 | 弹窗被盖、下拉穿模、元素重叠 | 层级差、遮挡关系、命中顺序 |
| **S（Z 剖面）** | 层级 × 状态 | 展开/选中/弹窗态位置不一致 | 每个状态下的层号、占位、可见性 |

**折叠归 Y，重叠归 Z。** 不要用 padding 去修另一个轴的问题，也不要用 z-index 去掩盖布局错误。

### 3. 轴可以随断点交换

桌面端 X 主导（分栏），移动端切到 Y 主导（堆叠）；这是**重新分配轴**，不是把桌面布局缩小。断点切换时必须重新画该断点的构造线，不能拿桌面线去套手机。

### 4. 构造线从 token 来

先定义“线”，再放元素：

- **外框线**：安全区、内容区左右边界、上下留白；
- **主分割线**：侧栏 / 主区 / 辅区，先定比例再放组件；
- **节奏线**：区块顶底、卡片顶底、列表行顶底；
- **角色基线**：标题基线、正文基线、控件中心线、图标中心线；
- **层线**：内容 0 / sticky 10 / 下拉 100 / 弹窗 200 / toast 300。

一条线至少服务两个元素；只服务一个元素的线是装饰，不是构造。线本身必须是 token 或具名常量，不能每页手画一套魔数。

### 5. 落子顺序

```text
画布 → 大区 → 区块 → 组件 → 内容
每一层：选主切轴 → 定比例 → 定缝 → 落子 → 验线
```

先有线，后有子；子往线上落；离线超过 1px 就是离群，不是“视觉误差”。

### 6. 与现有众数判定的关系

**设计时**：先画构造线，元素吸附到线。
**验收时**：量所有元素矩形边缘，聚类出众数线，离群者报 FAIL。

两者是同一套几何事实的正反两面：设计时线是输入，验收时线是输出。

## 组件尺寸映射（**起手可选值**）

| 类型 | xs | sm | md 默认 | lg |
|---|---:|---:|---:|---:|
| 控件高度 | 24 | 32 | 40 | 48 |
| 按钮 | - | 32 | 40 | 48 |
| 输入框 | 24 | 32 | 40 | 48 |
| 选择器/下拉 | 24 | 32 | 40 | 48 |
| 搜索栏 | - | 32 | 40 | 48 |
| 日期选择 | 24 | 32 | 40 | 48 |

- 表格行内按钮用 `sm`；页面表单 / 筛选栏 / 弹窗默认 `md`；营销页、大屏可用 `lg`。
- **同一行表单控件必须同高**；下拉面板宽度 ≥ 触发器宽度，最大高度 320，超出滚动。

|---|---:|---:|---|

| H1 | 28/36 | 600 | 页面标题 |

| H4 | 16/24 | 600 | 小标题 |
| Body | 14/22 | 400 | 正文 |
| Caption | 12/20 | 400 | 辅助说明 |

## 间距 / 圆角 / 阴影 / 层级（**起手可选值**）

- 间距：4、8、12、16、24、32、48、64。页面左右内边距 24/32；卡片 16/24/32；表单项 16/24；按钮组 8/12。
- 圆角：4、6、8、12、16、full。控件 6/8；卡片 8/12；弹窗 12/16。
- 阴影：none、sm、md、lg。卡片 `sm`、下拉 `md`、弹窗 `lg`。
- z-index：sticky **100**、dropdown **1000**、modal **2000**、toast **3000**。
  ⚠️ 与 `workbench-layout` 旧文档的 `10/150/200` 是同一语义的旧预算，**以本表为起手值**；但项目若已有自己的分布，**以项目为准**。

## 视觉层级

- L0 页面背景 · L1 页面区块/标题 · L2 卡片 · L3 卡片内分组 · L4 行内元素
- 嵌套超过 3 层是**信号不是禁令**：先用留白/分隔线/背景差降级视觉层级，确需保留嵌套时保证每层职责清晰；不要机械拆到信息架构变形。同一页面卡片圆角、阴影、内边距统一。
- 一个区域最多一个主按钮（区域的边界判定见「禁止项」）。危险操作只能用 `danger`，不能用 primary 红色代替。

## 按钮层级

`primary`（主操作，一个区域最多一个）· `default`/`secondary`（次操作）· `text`/`link`（弱操作）·
`danger`（删除与危险操作）· icon button 必须有可访问名称（桌面 hover tooltip；移动端用 aria-label 兜底）。
弹窗底部：取消 `default` + 确认 `primary`；删除弹窗：取消 `default` + 删除 `danger`。

## 组件选择决策树

固定选项少 → Select/Radio；固定选项多 → Select；可搜索 → AutoComplete/SearchSelect；
自由输入 → Input；筛选表单 → SearchBar；多选少 → Checkbox Group；多选多 → Select multiple；
日期 → DatePicker；日期范围 → RangePicker；操作 → Button。

## 组件清单的性质：触发清单，不是全集（**重要**）

**问：如果页面里有轮播、骨架屏、级联、树选择……而我们的 skill 里没有这些条目，实际操作中会不会漏掉？**

**答：会漏。机制不是"看不见"，而是"没有任何条目提醒它去检查那个维度"。**

实证（2026-09-18 同项目对照实验）：同一份代码、同一个可运行实例——
当 skill 里**没有**某条检查项时，两轮盲测都完全没碰它（报告结论甚至是"健康"）；
当我为那条轴**补了一个 Step + 一个脚本**后，下一轮立刻在浏览器里复现出问题。
→ **清单上没有的东西 = 不会被问 = 不会被查。** agent 的注意力是被 checklist 驱动的。

**但穷举组件是追不上的**：业务组件、自研组件、新组件会不断出现（光是常见清单就有 80+ 项）。所以正确做法是**两层**：

### 第一层：通用组件检查模板（不依赖清单，任何组件都套它）

对页面里出现的**每一个**组件（不管清单里有没有）过这 6 个维度：

| # | 维度 | 问什么 |
|---|---|---|
| 1 | **尺寸/刻度** | 高、圆角、内边距、字号，是否跟随项目众数？（跑审计脚本第一节） |
| 2 | **状态集** | 默认 / hover / focus / disabled / **loading** / **error** / **empty** 七态是否都定义了？没定义的状态会退化成什么样？ |
| 3 | **可达性** | 在零行、出错、门控未开、超宽这四种边界态下，它的操作入口还碰得到吗？（`debug-and-refactor` E13） |
| 4 | **跨页面一致性** | 同角色组件在其它页面的取值是否相同？（跑审计脚本第三节） |
| 5 | **复用判定** | 出现 ≥2 次就该抽公共；≥3 次必须抽（见「公共组件判定」） |
| 6 | **可访问性** | 有键盘可达？有 aria/role？焦点可见（注意 `outline:none` + 失效色 = 焦点不可见）？ |

### 第二层：差集发现（把"清单里没有的"自动找出来）

**不要靠人记住清单**，用一条命令扫出项目里实际用到的组件，再与本规范的已知条目比对：

```bash
# 项目里实际用到的组件（JSX 大写标签，按频次排序）
grep -rhoE '<[A-Z][A-Za-z0-9]*' src --include=*.tsx --include=*.jsx | sort | uniq -c | sort -rn | head -40
```

- **频次 ≥ 2 的** = 项目自有组件 → 逐个套上面的 6 维模板；
- **第三方库组件**（ant-design / MUI / shadcn 等）→ 查是否统一版本与用法、有无被二次封装（没封装 = 以后改不动）；
- **与本规范清单的差集**（即"项目用到但规范没登记的"）→ **强制套模板**，因为它们最容易没人管。

### 已知空白（2026-09-18 实测：28 个常见组件里 17 个无条目）

`轮播 / 水印 / 级联 / 树选择 / 上传 / 滑块 / 评分 / 气泡确认 / 步骤条 / 锚点 /
返回顶部 / 看板 / 权限树 / 图标按钮 / 徽章 / 时间线 / 描述列表`

→ **不要急着逐个补条目**（补了也追不上新组件）。遇到它们时**直接套上面的通用模板**，
若某个组件反复出问题，再把它升格为清单里的正式条目。

## 触发清单（完整，用来提醒"别忘了还有这些"）

**这份清单的作用只有一个：提醒。** 它不是全集、不要求全都有条目 —— 遇到清单里的东西，

## 还有哪些维度会漏（**不在组件清单里的**）

组件清单回答的是"有哪些东西"，但真正漏得最多的是**"每个东西的状态和边界"**。下面这些维度不在任何组件清单里，却是最常出问题的：

| # | 维度 | 典型漏法 |
|---|---|---|
| 1 | **状态集**（默认/hover/active/**focus-visible**/disabled/**loading**/**error**/**empty**） | 只写了默认态，其它态退化成"没反应"或"空白" |
| 2 | **可访问性** | 键盘不可达；`outline:none` + 失效色 = **焦点完全不可见**；无 aria/role；对比度 <4.5:1；未处理 `prefers-reduced-motion`；触摸目标 <44px |
| 3 | **多主题 / 暗色** | token 只在浅色主题有定义 → 深色下**静默失效**（见 `debug-and-refactor` E12） |
| 4 | **数据格式与空值** | 千分位、百分比、日期时间格式、文件大小单位、**空值占位**（`—` / `0` / "暂无"）各页面不统一 —— 多页面不一致的重灾区 |
| 5 | **文案一致性** | 同一动作不同叫法（删除/移除/销毁）、按钮动词 vs 名词、句末标点、大小写 |
| 6 | **状态作用域与多实例** | 多标签 / 多弹窗 / 多图表时，state 是否按**视图身份**分隔（反例：在 A 库标签执行查询，切到 B 库标签仍显示 A 的结果） |
| 7 | **加载与竞态** | 重复请求、后发先至、取消、超时、重试 —— 尤其"筛选/翻页/切标签"连点时 |
| 8 | **动效** | 时长与缓动是否统一；未响应 `prefers-reduced-motion`；动画触发 layout thrash |
| 9 | **边界数据** | 超长文本、超宽表格、0 行 / 1 行 / 10000 行、极端数值、空字符串 vs null |
| 10 | **组件 API 一致性** | 同类组件的 props / 事件命名是否统一（`size` vs `scale`、`value` vs `modelValue`、`onChange` vs `onUpdate`）—— 不统一的话，抽公共组件时会卡死 |
| 11 | **反馈一致性** | 成功/失败提示的位置与时长、破坏性操作二次确认的措辞 |
| 12 | **图标规范** | 尺寸档位、线宽、风格（线性 vs 面性）、图标与文字间距；emoji 当图标见 `no-emoji-ui` |
| 13 | **表格专项** | 列宽策略、粘性表头、横向滚动、行内操作、批量选择、分页位置 |
| 14 | **打印与缩放** | 打印样式、浏览器 200% 缩放、窄屏 320px |

这些维度**不依赖组件清单**：页面里出现任何组件，都该按这 14 条过一遍（配合上面的 6 维模板）。

## 页面骨架与跨页面一致（**本规范的重点**）

**标准页面骨架**（间距取项目自身的众数，跨页面必须一致）：

```
页头(标题 + 主操作) → 筛选/查询区 → 内容区(卡片/表格) → 分页区
```

**跨页面一致性核对清单**（改任何一页时过一遍，也可直接用脚本的"跨文件分歧"一节）：

1. 同角色控件（按钮/输入框/下拉/搜索栏）在**所有页面**的高、圆角、字号、内边距是否一致？
2. 页头结构（标题层级 + 主操作位置）是否一致？
3. 筛选区的控件高度、label 宽度与对齐、校验提示位置是否一致？
4. 空态、加载态、错误态是否**复用同一套**（不是每页自己画）？
5. 分页区位置与样式是否一致？
6. 响应式断点是否统一（而不是各页自写 `@media (max-width: 1234px)`）？

## 三态统一（空态 / 加载态 / 错误态）

| 状态 | 统一要求 |
|---|---|
| 空态 | 复用同一组件：图标 + 一句说明 + **最多一个**行动按钮；按钮必须**常驻可达**（见 `debug-and-refactor` E13：别把空态塞进 `colSpan` 的 `<td>`，宽表下会被推到视口外） |
| 加载态 | 表格/列表用**骨架屏**，局部操作用 spinner，整页用遮罩；同一区域不能三种混用 |
| 错误态 | 复用同一组件：图标 + 语义化文案 + 重试入口；文案要说清"什么错了 + 下一步" |

## 公共组件判定（接 `debug-and-refactor` Part B）

**阈值**：同一段 UI **出现 ≥ 2 次**就该抽；**≥ 3 次**必须抽。

**判定三问**（全过 = 抽）：① 是否在两个及以上页面/模块出现？
② 差异是否只是**变体**（尺寸档位/颜色/有无图标）而非结构不同？
③ 未来新增同类时，是否希望它自动保持一致？

**抽的纪律**：只暴露变体参数，**不暴露"任意样式入口"**；只能扩展变体、不能改基础尺寸；
抽之前确认它不是"看起来像、语义不同"（表格内删除按钮 vs 弹窗底部删除按钮）。

## 禁止项（每条带适用边界）

- 禁止同一角色控件在不同页面取不同尺寸（头号禁止项；先判"角色"——营销页主按钮与表格行内按钮本就是不同角色，不算违反）。
- 禁止一个**区域**内多个主按钮（区域 = 用户视线的一个焦点组；卡片列表每卡各带一个主按钮不算违反，它们各自是所在卡的区域主按钮。营销页 hero 与页头 CTA 同屏时，让其中一个降为 secondary）。
- 禁止下拉宽度和触发器不一致（可机械验证，无例外）。
- 禁止每个页面自己写一套按钮、卡片、搜索栏（同 B3/B4：有组件库走组件库，vanilla 走既有类与模式）。
- 禁止"看起来差不多"就新造一个组件（先跑「公共组件判定」三问）。
- rgba 阴影：有 shadow token 走 token；无 token 时集中定义一次，禁止同一阴影值在文件里抄三份。

## 实测补遗（2026-10-24 · vanilla HTML/CSS 项目 spare-cat）

来源：用户截图报告"侧栏按钮图标换行"。审计脚本与组件清单都没拦住，逐条补进方法论：

### 1. 「无 class 按钮」盲区（脚本扫不到）

vanilla 项目里大量 `<button>` **不带 class**，靠容器后代选择器样式化（`.aside-contact button`、`.aside-editorial button`、`.profile-menu button`…）。
审计脚本按 class/props 统计 → 这类按钮完全不在样本里。

**检查项**：扫出所有无 class 的 `<button>`（含图标的），逐一核对其容器选择器是否给了 **flex 基准布局**：

```bash
# 提取无 class 但含图标的按钮及其容器线索
node -e "const src=require('fs').readFileSync('app.js','utf8');
const re=/<button([^>]*)>([\s\S]{0,200}?)<\/button>/g;let m;
while((m=re.exec(src))){if(!/class=\"/.test(m[1])&&m[2].includes('\${icon('))console.log(m[1],m[2].replace(/\s+/g,' ').slice(0,40))}"
```

### 2. 图标布局的隐含父容器假设

全局 `.icon { flex: 0 0 auto }` **隐含"父容器是 flex/grid"**。放进 inline-block 按钮时，
SVG 计算样式为 block → 图标独占一行、文字被挤到下一行，且不同容器表现不一。

**检查项**：对每个"图标+文字"按钮验证 icon 与文字是否同行。启发式（**低可靠，必须截图人工核实**）：

```js
// 浏览器控制台全页扫：按钮非 flex/grid 且内部 .icon computed display 为 block → 候选
Array.from(document.querySelectorAll('button,a')).filter(b => {
  const icon = b.querySelector('.icon');
  if (!icon || !b.textContent.trim()) return false;
  if (/flex|grid/.test(getComputedStyle(b).display)) return false;
  return getComputedStyle(icon).display === 'block';
}).map(b => b.textContent.trim().slice(0, 14))
```

误报案例：同项目 `.rail-post`（icon block 但视觉横排正常）——启发式只当候选清单，最终以截图为准。

### 3. 同角色离群的排查入口

同一页面里同角色按钮一个正常一个换行时，**直接 diff 两者的容器选择器 CSS**：
先比对 `display`（是否 flex），再比对字号/对齐/行高。本例：`.rail-section-head button`（inline-flex ✅）vs `.aside-contact button`（无 display ❌），一次定位。

### 4. 用户截图是最便宜的测试用例

用户圈红截图里的两个按钮，恰好是"出现 ≥2 次就该抽公共"的反例：同角色（侧栏主操作）、
同视觉（moss 底白字）、却分属两个互不复用的裸选择器。修法是把后到的对齐到先前的刻度，
而不是各修各的——与「跨文件分歧优先修」同一逻辑。

### 5. 弹窗关闭途径冗余时，角标 × 可省略（同日续补）

短表单弹窗（无标题行、首行即控件）里，右上角 × 会侵占首行控件空间：留位则整行右缩、
与下方输入框右缘错位；不留位则压住控件。若该弹窗已有 ≥2 条关闭途径
（遮罩点击 / 底部取消按钮 / Esc），× 是冗余项，直接隐藏更干净：

```css
.modal:has(.short-form-modal) .modal-close { display: none; }
```

判定：数一数 × 之外还有几条关闭途径——≥2 条且弹窗顶部无标题区，就去 ×；
内容长、需要随时中断阅读的长弹窗（详情页、文章）保留 ×。

### 6. 圆形头像徽章（双层同心圆）的三连击（同项目 v008 实测）

用户报告"头像外圈是椭圆、两层不同心"。三层原因叠加，每一层单独看都不算错：

1. **宽泛 span 选择器误伤**：`.review-web-head span { margin-left: 3px }` 本意给日期文字，
   却命中了头像的两层 `<span>`（内圈文字右偏 3px、外圈右移 3px）——**直接导致不同心**。
   修法：收窄为 `.review-web-head div span`，让结构承载意图。
2. **怪值覆盖档位**：`.contributor-avatar .avatar { width: 29px }` 覆盖了既有的 26/28 两档
   （29 既不是基准也不是新档位，是"写错一位"的离群值）。用「命中规则清单」法定位：
   遍历 styleSheets 收集目标元素 matches 的所有规则，按序排列，最后一条胜出者就是真凶。
3. **环形容器无正方约束**：外圈（描述性边框环）`display: grid; padding: 2px; border-radius: 50%`
   但没有尺寸约束 → 被上下文拉伸成 38×35 椭圆。修法：`width/height: fit-content; line-height: 0;`
   → 外圈 = 内容 + padding + border，天然正方。

**同心圆环徽章检查项**：对每一层量 `getBoundingClientRect`，外圈必须正方（w === h）、
内圈 dx === dy；再对照「命中规则清单」确认尺寸来自哪一档。

**通用教训**：`border-radius: 50%` 在非正方盒上是椭圆不是圆——**任何"圆形"元素都要先验证 w === h**；
而"不同心"最常见的来源不是对齐属性，是**误伤的 margin/padding 把某一层推歪了**。

### 7. 弹窗态是独立检查面（同项目 v010 续补）

页面级扫描**扫不到弹窗内部**：弹窗要逐个打开、逐个量。之前的全局走查扫了 7 个页面，
但「× 压住右上角文字」的同类问题在猫详情弹窗里依然存在——因为检查面里没有"弹窗"这一层。

**弹窗检查清单**（每个弹窗都过）：
1. **× 与首行文字重叠**：用**文字实际范围**（`Range.getBoundingClientRect`）判重叠，
   别用元素盒——块级容器盒子天然横跨全宽，盒重叠是正常的，文字重叠才是问题；
2. **头像/徽标与相邻文字的间距**（gap < 8px 时视觉上"粘"在一起，用户会报"重叠"）；
3. 打开方式：优先走真实 UI 路径（点按钮打开），直接调函数要注意依赖 state 的一致性。

```js
// × 与弹窗内可见文字重叠检测（文字级，挂 window.checkClose 后逐弹窗调用）
window.checkClose = () => {
  const close = document.querySelector('.modal-close');
  if (!close) return 'NO CLOSE BTN';
  const cr = close.getBoundingClientRect();
  const offenders = [];
  const walk = (el) => { for (const child of el.children) {
    if (child.closest('.modal-close')) continue;
    const hasText = Array.from(child.childNodes).some(n => n.nodeType === 3 && n.textContent.trim());
    if (hasText) {
      const range = document.createRange(); range.selectNodeContents(child);
      const r = range.getBoundingClientRect();
      if (r.width && r.height && r.right > cr.left + 3 && r.left < cr.right && r.top < cr.bottom && r.bottom > cr.top)
        offenders.push(child.className.toString().slice(0, 20));
    }
    walk(child);
  } };
  walk(document.querySelector('.modal'));
  return offenders.length ? 'OVERLAP: ' + offenders.join('|') : 'clean';
};
```

### 8. 同模式第三例：`.detail-web-publisher span { display: block }`（v011 实测）

与补遗 7 的 `.review-web-head span` 完全同构：给"名字下方的 meta 文字 span"设样式，
选择器却写成 `.容器 span` → 误伤同容器内的**头像 span**，把 `.avatar` 的
`display: grid; place-items: center` 覆盖成 `block`（特异性 类+元素 > 类）→
圆内文字退回文档流排到左上角，用户看到"字不在圆心"。

**排查凭证**：`getComputedStyle(avatar).display` 为 block 而非 grid；
再用「命中规则清单」法列出所有含 `display` 的命中规则，最后一条胜出者即覆盖者。

**修复**：收窄为 `.detail-web-publisher > div span`（meta span 在 div 内，头像 span 是直接子级）。

**规则（v2，含适用边界——禁令不加分档会变成教条）**：这是同项目第三次
"容器级 span/descendant 选择器误伤图标元素"，但问题**不在 `.容器 span` 这个写法本身**，
而在**容器内混排了不同角色的 span**。按容器内 span 的角色构成分三档：

- **混排容器**（图标/图形 span 与文本 span 同容器）→ 宽泛选择器必须隔离：
  `> div span`、`:not(.avatar)` 或给图标 span 挂专属类；
- **纯文本容器**（所有 span 都是同角色的文字，如署名行的日期、徽章）→
  `.容器 span` 合法且简洁，**可以继续用**——不要因为这条规则把合理实现吓退；
- **判定方法**：列出容器内全部 span 的角色（是否含图标/图形元素）与 computed display，
  角色单一才允许宽泛写法；**往纯文本容器里新增图标时，必须回头收窄旧选择器**。

检查项：对每个含图标的容器，列出其内部 span 的 computed display 是否与设计一致。

**写规则的元教训**：禁令必须带适用边界，否则审查者会把它当教条执行——
把"混排结构下全禁"错用成"见到这类结构的需求直接绕开"，合理实现反而被规则吓跑。
沉淀进 skill 的条款统一用「症状 → 根因 → 分档规则（含何时不适用）→ 判定命令」的格式。

### 9. 重叠的静态可证性：先算几何，再上浏览器（v011 复盘）

"碰撞必须浏览器量"只对了 2/4——复盘四个案例的修复前后代码 diff，其中 **2 个可纯静态证明**：

**静态可证子类一：绝对定位元素 × 边缘对齐内容**（× 压住"1.3 KM AWAY"）。
把规则翻译成矩形：× 绝对定位 `right:12; width:35` → 占据 [W−47, W−12]；
kicker `justify-content: space-between` 把右侧文字钉到容器右缘 → 文字右端 = W−29（padding 29）。
W−29 > W−47 → 必然相交，与屏幕宽度无关。修复 `padding-right: 44px` → 文字右端 W−73，
间隙 26px——**与浏览器实测 27px 差 1px**（边框取整）。

**静态可证子类二：特异性覆盖 display/对齐**（"周"字不居中）。
`.detail-web-publisher span { display:block }`（0,1,1）压过 `.avatar { display:grid;
place-items:center }`（0,1,0）→ block 下文字按普通流排 → 预测文字在盒原点 (0,0)。实测 (0,1)——吻合。
修复后 grid 恢复 → 预测 dx=(31−13)/2=9、dy=(31−12)/2=9.5。实测 9 / 9.5——**分毫不差**。

**必须浏览器子类**（静态推不出）：
- 双圆椭圆 38×35：外圈无显式宽高，尺寸由 flex 拉伸+内容共同决定，静态需完整模拟布局引擎；
- 图标换行：可见规则里没有任何一条把 .icon 设为 block，按规则静态读会得出"应该同行"的
  错误结论——存在当时未找到的规则或 UA 行为，可见代码不足以解释渲染。

**方法论定稿（两层）**：
1. **先静态**：对怀疑重叠的组合做"几何翻译 + 求交"（绝对定位盒、边缘对齐、特异性覆盖是三大可证模式），
   修复前后各算一遍，数字对得上即证明因果；
2. **再浏览器**：静态无法定论（上下文相关尺寸、未解释渲染）或需要整体目检时，量矩形 + 截图。
   量矩形仍是**最终裁决**（它就是真实渲染），静态推导是**便宜的前置预测与回归手段**。

### 10. 全页重叠扫描：浮层 × 文字矩阵（v011 全站回归实测）

补遗 7 是弹窗版。全页版要额外解决一个问题：**absolute 元素里混着两种语义**——
真浮层（角标、关闭钮、中心图钉，叠在别人身上是它的职责）和**布局容器**
（地图画布、照片块，恰好用了 absolute 但占据自己的文档流位置）。不分清就会满屏误报。

**扫描器设计**（挂 window.scanOverlap 后逐页调用）：
1. **O 集**：computed position 为 absolute/fixed 的元素（子树整体算一个浮层，不再下钻）；
2. **T 集**：有直接文本子节点的元素，用 **Range rect**（文字实际范围）；
3. **排除清单**（SKIP 正则）：leaflet 内部、装饰纹理（grain/texture）、瞬态（toast）、
   照片/画布类布局容器（photo-slot、detail-web-photo、live-map、mini-map…）、隐藏文件输入、
   已单测的弹窗家族——**排除清单就是"已知有意叠置"的登记表，每豁免一个要能说出理由**；
4. **全屏容器判定**：rect > 92%×85% 视口的 absolute 元素不是浮层，继续走子树（否则弹窗/全屏地图内容全漏）；
5. 报 O × T 相交对（互不为祖先、交区 > 3×3px），按面积排序，**逐对截图人工核验**。

**视口矩阵**：1280 / 390 / 320 × 全部页面，另加**滚动到底专项**——
fixed 底栏（tabbar）与滚到底后的最后一段文字是否有遮挡（本质是查 main 的 padding-bottom 是否预留）。

实测结论（spare-cat v011）：桌面 6 页 + 移动 6 页 + 窄屏 3 页 + 底栏专项，**全部 0 相交**；
13 个浮层逐一归类为设计意图（角标叠图、收藏钮叠照片、中心图钉）。
与静态可证子类（补遗 9）互补：静态算"这对规则会不会撞"，本扫描查"全站现在有没有撞"。
