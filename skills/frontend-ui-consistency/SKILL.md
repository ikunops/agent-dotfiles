# 前端 UI 一致性规范

## 核心立场（先读这段）

> **数值没有绝对标准，一致性才有。**
> 不同项目的字号、控件尺寸差一两号是完全正常的 —— 14px 正文还是 13px 正文，32 还是 36 的控件，都不构成"错"。
> **唯一要保障的是：同一个程序里，A 页面、B 页面、C 页面必须一致。**
> A 页面用尺寸 1、B 页面用尺寸 2，这才是问题。

所以本规范的工作方式是**相对的**：

1. **先清点**：统计项目里各类字面量的真实分布，得出**事实基准**（众数）。
2. **找离群**：只出现一两次的**长尾值** = 嫌疑（往往就是"某个页面独有的怪值"）。
3. **查跨文件分歧**：某个文件的主流值与全局众数不同 = **最该修**的那一类。

判定规则与汇报格式沿用 `ui-acceptance` 的「**横向一致性（众数判定）**」：
**取众数为基准，离群者报 FAIL**，汇报固定为《**N 处中 M 处是 X，这 K 处是 Y**》——不许笼统说"基本一致"。

⚠️ **下面几张数值表只是"新项目起手可选值"**，不是强制标准：
项目还没有自己的刻度时可以用它起步；**一旦项目已有分布，以项目的为准**（用脚本统计出来）。

## 一键审计（这才是主要用法）

```bash
python scripts/audit_ui_consistency.py --root web/src
python scripts/audit_ui_consistency.py --root web/src --out ui-audit.md
python scripts/audit_ui_consistency.py --root web/src --props font,height --max-list 10
```

输出四节：**项目事实基准（众数）→ 长尾离群 → 跨文件分歧 → 怎么改**。

- **长尾离群** = 出现 ≤2 次或 ≤1% 的值（**非众数不等于不一致**：一个项目本来就有多个合法角色档位，如正文/说明/标题）。
- **跨文件分歧**优先修 —— 它直接对应"A 页面一个值、B 页面另一个值"。
- 用 `var(--x)` 的地方**不参与判定**（已 token 化是好事）。

## 三个入口

| 场景 | 怎么用 |
|---|---|
| **开发中**（写新页面/组件） | 新值先问：**项目里有没有现成的同类值？** 有就跟随，不要引入新值；确实需要新档位，就同步更新到所有同类位置 |
| **审查 / debug / 优化** | 作为**判定基准**：`frontend-review-squad` Step 2 用它做越界判定（此前只有"统计"没有"基准"）；先跑脚本 |
| **判断要不要抽公共组件** | 见文末「公共组件判定」（阈值 + 三问），接 `debug-and-refactor` Part B |

> 与其它前端 skill 的分工：本文件管**一致性与刻度**；`design-taste-frontend` 管审美方向；
> `workbench-layout` 管工作台布局硬规则；`layout-guardrails` 管溢出与可收缩性；`hallmark` 管反 AI 味。

## 强制原则

1. 禁止硬编码颜色、字号、间距、圆角、阴影、z-index（用 `var(--x)` / token）。
2. 只能使用 `design-tokens` 和现有组件库。
3. 写新 UI 前，先搜索项目里是否已有相似组件和页面。
4. **同一区域内的控件高度、圆角、间距必须一致**。
5. 新组件只能**扩展变体**，不能改基础尺寸。
6. Token 里没有合适值时，选**最接近的**，不能自己造 —— 若造了新值，必须同步到所有同类位置。

## 组件尺寸映射（**起手可选值**）

| 类型 | xs | sm | md 默认 | lg |
|---|---:|---:|---:|---:|
| 控件高度 | 24 | 32 | 40 | 48 |
| 按钮 | - | 32 | 40 | 48 |
| 输入框 | 24 | 32 | 40 | 48 |
| 选择器/下拉 | 24 | 32 | 40 | 48 |
| 搜索栏 | - | 32 | 40 | 48 |
| 日期选择 | 24 | 32 | 40 | 48 |

- 表格行内按钮用 `sm`；页面表单 / 筛选栏 / 弹窗默认 `md`；营销页、大屏可用 `lg`。
- **同一行表单控件必须同高**；下拉面板宽度 ≥ 触发器宽度，最大高度 320，超出滚动。

## 字体层级（**起手可选值**）

| 层级 | 字号/行高 | 字重 | 用途 |
|---|---:|---:|---|
| Display | 32/40 | 700 | 营销大标题 |
| H1 | 28/36 | 600 | 页面标题 |
| H2 | 24/32 | 600 | 区块标题 |
| H3 | 20/28 | 600 | 卡片标题 |
| H4 | 16/24 | 600 | 小标题 |
| Body | 14/22 | 400 | 正文 |
| Caption | 12/20 | 400 | 辅助说明 |

## 间距 / 圆角 / 阴影 / 层级（**起手可选值**）

- 间距：4、8、12、16、24、32、48、64。页面左右内边距 24/32；卡片 16/24/32；表单项 16/24；按钮组 8/12。
- 圆角：4、6、8、12、16、full。控件 6/8；卡片 8/12；弹窗 12/16。
- 阴影：none、sm、md、lg。卡片 `sm`、下拉 `md`、弹窗 `lg`。
- z-index：sticky **100**、dropdown **1000**、modal **2000**、toast **3000**。
  ⚠️ 与 `workbench-layout` 旧文档的 `10/150/200` 是同一语义的旧预算，**以本表为起手值**；但项目若已有自己的分布，**以项目为准**。

## 视觉层级

- L0 页面背景 · L1 页面区块/标题 · L2 卡片 · L3 卡片内分组 · L4 行内元素
- 不要卡片套卡片套卡片（>3 层必须拆）。同一页面卡片圆角、阴影、内边距统一。
- 一个区域最多一个主按钮。危险操作只能用 `danger`，不能用 primary 红色代替。

## 按钮层级

`primary`（主操作，一个区域最多一个）· `default`/`secondary`（次操作）· `text`/`link`（弱操作）·
`danger`（删除与危险操作）· icon button 必须有 tooltip。
弹窗底部：取消 `default` + 确认 `primary`；删除弹窗：取消 `default` + 删除 `danger`。

## 组件选择决策树

固定选项少 → Select/Radio；固定选项多 → Select；可搜索 → AutoComplete/SearchSelect；
自由输入 → Input；筛选表单 → SearchBar；多选少 → Checkbox Group；多选多 → Select multiple；
日期 → DatePicker；日期范围 → RangePicker；操作 → Button。

## 组件清单的性质：触发清单，不是全集（**重要**）

**问：如果页面里有轮播、骨架屏、级联、树选择……而我们的 skill 里没有这些条目，实际操作中会不会漏掉？**

**答：会漏。机制不是"看不见"，而是"没有任何条目提醒它去检查那个维度"。**

实证（2026-09-18 同项目对照实验）：同一份代码、同一个可运行实例——
当 skill 里**没有**某条检查项时，两轮盲测都完全没碰它（报告结论甚至是"健康"）；
当我为那条轴**补了一个 Step + 一个脚本**后，下一轮立刻在浏览器里复现出问题。
→ **清单上没有的东西 = 不会被问 = 不会被查。** agent 的注意力是被 checklist 驱动的。

**但穷举组件是追不上的**：业务组件、自研组件、新组件会不断出现（光是常见清单就有 80+ 项）。所以正确做法是**两层**：

### 第一层：通用组件检查模板（不依赖清单，任何组件都套它）

对页面里出现的**每一个**组件（不管清单里有没有）过这 6 个维度：

| # | 维度 | 问什么 |
|---|---|---|
| 1 | **尺寸/刻度** | 高、圆角、内边距、字号，是否跟随项目众数？（跑审计脚本第一节） |
| 2 | **状态集** | 默认 / hover / focus / disabled / **loading** / **error** / **empty** 七态是否都定义了？没定义的状态会退化成什么样？ |
| 3 | **可达性** | 在零行、出错、门控未开、超宽这四种边界态下，它的操作入口还碰得到吗？（`debug-and-refactor` E13） |
| 4 | **跨页面一致性** | 同角色组件在其它页面的取值是否相同？（跑审计脚本第三节） |
| 5 | **复用判定** | 出现 ≥2 次就该抽公共；≥3 次必须抽（见「公共组件判定」） |
| 6 | **可访问性** | 有键盘可达？有 aria/role？焦点可见（注意 `outline:none` + 失效色 = 焦点不可见）？ |

### 第二层：差集发现（把"清单里没有的"自动找出来）

**不要靠人记住清单**，用一条命令扫出项目里实际用到的组件，再与本规范的已知条目比对：

```bash
# 项目里实际用到的组件（JSX 大写标签，按频次排序）
grep -rhoE '<[A-Z][A-Za-z0-9]*' src --include=*.tsx --include=*.jsx | sort | uniq -c | sort -rn | head -40
```

- **频次 ≥ 2 的** = 项目自有组件 → 逐个套上面的 6 维模板；
- **第三方库组件**（ant-design / MUI / shadcn 等）→ 查是否统一版本与用法、有无被二次封装（没封装 = 以后改不动）；
- **与本规范清单的差集**（即"项目用到但规范没登记的"）→ **强制套模板**，因为它们最容易没人管。

### 已知空白（2026-09-18 实测：28 个常见组件里 17 个无条目）

`轮播 / 水印 / 级联 / 树选择 / 上传 / 滑块 / 评分 / 气泡确认 / 步骤条 / 锚点 /
返回顶部 / 看板 / 权限树 / 图标按钮 / 徽章 / 时间线 / 描述列表`

→ **不要急着逐个补条目**（补了也追不上新组件）。遇到它们时**直接套上面的通用模板**，
若某个组件反复出问题，再把它升格为清单里的正式条目。

## 还有哪些维度会漏（**不在组件清单里的**）

组件清单回答的是"有哪些东西"，但真正漏得最多的是**"每个东西的状态和边界"**。下面这些维度不在任何组件清单里，却是最常出问题的：

| # | 维度 | 典型漏法 |
|---|---|---|
| 1 | **状态集**（默认/hover/active/**focus-visible**/disabled/**loading**/**error**/**empty**） | 只写了默认态，其它态退化成"没反应"或"空白" |
| 2 | **可访问性** | 键盘不可达；`outline:none` + 失效色 = **焦点完全不可见**；无 aria/role；对比度 <4.5:1；未处理 `prefers-reduced-motion`；触摸目标 <44px |
| 3 | **多主题 / 暗色** | token 只在浅色主题有定义 → 深色下**静默失效**（见 `debug-and-refactor` E12） |
| 4 | **数据格式与空值** | 千分位、百分比、日期时间格式、文件大小单位、**空值占位**（`—` / `0` / "暂无"）各页面不统一 —— 多页面不一致的重灾区 |
| 5 | **文案一致性** | 同一动作不同叫法（删除/移除/销毁）、按钮动词 vs 名词、句末标点、大小写 |
| 6 | **状态作用域与多实例** | 多标签 / 多弹窗 / 多图表时，state 是否按**视图身份**分隔（反例：在 A 库标签执行查询，切到 B 库标签仍显示 A 的结果） |
| 7 | **加载与竞态** | 重复请求、后发先至、取消、超时、重试 —— 尤其"筛选/翻页/切标签"连点时 |
| 8 | **动效** | 时长与缓动是否统一；未响应 `prefers-reduced-motion`；动画触发 layout thrash |
| 9 | **边界数据** | 超长文本、超宽表格、0 行 / 1 行 / 10000 行、极端数值、空字符串 vs null |
| 10 | **组件 API 一致性** | 同类组件的 props / 事件命名是否统一（`size` vs `scale`、`value` vs `modelValue`、`onChange` vs `onUpdate`）—— 不统一的话，抽公共组件时会卡死 |
| 11 | **反馈一致性** | 成功/失败提示的位置与时长、破坏性操作二次确认的措辞 |
| 12 | **图标规范** | 尺寸档位、线宽、风格（线性 vs 面性）、图标与文字间距；emoji 当图标见 `no-emoji-ui` |
| 13 | **表格专项** | 列宽策略、粘性表头、横向滚动、行内操作、批量选择、分页位置 |
| 14 | **打印与缩放** | 打印样式、浏览器 200% 缩放、窄屏 320px |

这些维度**不依赖组件清单**：页面里出现任何组件，都该按这 14 条过一遍（配合上面的 6 维模板）。

## 页面骨架与跨页面一致（**本规范的重点**）

**标准页面骨架**（间距取项目自身的众数，跨页面必须一致）：

```
页头(标题 + 主操作) → 筛选/查询区 → 内容区(卡片/表格) → 分页区
```

**跨页面一致性核对清单**（改任何一页时过一遍，也可直接用脚本的"跨文件分歧"一节）：

1. 同角色控件（按钮/输入框/下拉/搜索栏）在**所有页面**的高、圆角、字号、内边距是否一致？
2. 页头结构（标题层级 + 主操作位置）是否一致？
3. 筛选区的控件高度、label 宽度与对齐、校验提示位置是否一致？
4. 空态、加载态、错误态是否**复用同一套**（不是每页自己画）？
5. 分页区位置与样式是否一致？
6. 响应式断点是否统一（而不是各页自写 `@media (max-width: 1234px)`）？

## 三态统一（空态 / 加载态 / 错误态）

| 状态 | 统一要求 |
|---|---|
| 空态 | 复用同一组件：图标 + 一句说明 + **最多一个**行动按钮；按钮必须**常驻可达**（见 `debug-and-refactor` E13：别把空态塞进 `colSpan` 的 `<td>`，宽表下会被推到视口外） |
| 加载态 | 表格/列表用**骨架屏**，局部操作用 spinner，整页用遮罩；同一区域不能三种混用 |
| 错误态 | 复用同一组件：图标 + 语义化文案 + 重试入口；文案要说清"什么错了 + 下一步" |

## 公共组件判定（接 `debug-and-refactor` Part B）

**阈值**：同一段 UI **出现 ≥ 2 次**就该抽；**≥ 3 次**必须抽。

**判定三问**（全过 = 抽）：① 是否在两个及以上页面/模块出现？
② 差异是否只是**变体**（尺寸档位/颜色/有无图标）而非结构不同？
③ 未来新增同类时，是否希望它自动保持一致？

**抽的纪律**：只暴露变体参数，**不暴露"任意样式入口"**；只能扩展变体、不能改基础尺寸；
抽之前确认它不是"看起来像、语义不同"（表格内删除按钮 vs 弹窗底部删除按钮）。

## 禁止

- 禁止同一角色控件在不同页面取不同尺寸（这是本规范的头号禁止项）。
- 禁止随意写 rgba 阴影、禁止一个页面多个主按钮。
- 禁止下拉宽度和触发器不一致。
- 禁止每个页面自己写一套按钮、卡片、搜索栏。
- 禁止自己发明"看起来差不多"的组件。

## AI 输出前自查

- [ ] 新引入的值，项目里**已有同类值**吗？有就跟随。
- [ ] 同区域按钮高度一致？表单控件高度一致？
- [ ] 跨页面同角色控件取值一致？（跑脚本看"跨文件分歧"）
- [ ] 标题层级按项目既有档位？卡片不超过 3 层？
- [ ] 只有一个主按钮？空/加载/错误态复用同一套？
- [ ] 是否跑了 `python scripts/audit_ui_consistency.py --root <前端源码>`？

## 脚本的可靠性分级

- **高可靠**：某值出现几次、众数是谁 —— 计数事实。
- **低可靠**：*"这一处离群是不是错"* —— 刻意设计、第三方覆盖、对齐补偿、语义层级不同都会离群，**必须人工核实后才可采信**。
