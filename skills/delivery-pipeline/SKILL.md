# 交付流水线 (Delivery Pipeline)

你是**调度器**，不亲自干重活：每个阶段加载对应 skill 去干活，你负责判定任务类型、把守阶段门禁、维护流水线台账。模型执行、skill 是规程、台账是状态——三者缺一不可。

## 第一步：判定任务类型（决定走哪条流水线）

| 信号 | 流水线 |
|---|---|
| 提到参考项目 / 倒模 / 仿照 / 对齐某开源实现 / "照着它做" | **P1 倒模交付** |
| 全新项目或全新大模块，从零开始 | **P2 全新交付** |
| 报错 / 行为不对 / "修一下" / 指向具体缺陷 | **P3 修复** |
| 已有项目加功能（无参考项目语境） | **P4 增量** |

判定纪律：

- **信号优先级：P3 > P1 > P4 > P2**。用户说"修"就是修，不许擅自升级成重做。
- 含糊时**选轻的那条**，并在开工第一句说明"按 P4 增量走，理由 X"。
- 单点小任务（预计半小时内、不跨阶段）**不进流水线**，直接干——流水线是为长任务设计的，杀鸡用牛刀是浪费。
- 判定错了随时可换线：在台账上记"换线 P2→P1，原因"，从对应阶段继续，已完成的阶段不重跑。

## 流水线编排（阶段 → 加载的 skill → 出场条件）

### P1 倒模交付（参考项目 → 交付）

| # | 阶段 | 加载 | 出场条件（不满足不许进下一阶段） |
|---|---|---|---|
| 1 | 测绘 | `project-cartographer`（倒模模式） | 05-insights 有可借鉴点 + 测绘台账闭环（无 🚧）；**参考项目的结构维度（层级/分组/步骤/级别）已做"真结构 vs 装饰"判定并记入 insights** |
| 2 | 规划 | 无（用 cartographer 的 insights） | 开发任务清单落盘；清单按实现经济学排过序（能复用则复用、实现能轻则轻）；**功能范围只由用户增删——agent 对范围只有建议权** |
| 3 | 开发 | `ponytail`（常驻人格）；前端任务按需加 `frontend-design`/`shadcn`，后端按栈加对应 skill | 任务清单全部勾掉；每项有落盘产物 |
| 4 | 调试 | `debug-and-refactor` | 清单相关回归无已知 broken；发现的问题入台账而非口头记 |
| 5 | 审查 | `ponytail-review`（对 diff）；改动面大加 `ponytail-audit`；前端改动加 `frontend-review-squad`（含 cartographer 闭环测绘）；页面级验收走 `ui-acceptance` | delete-list 清零，或每条保留项有一行理由；**删除涉及用户可见功能或共享基础设施时，先过用户**；审查发现的问题入台账而非口头记 |
| 6 | 交付 | 无 | 汇总报告：做了什么 / 删了什么 / 剩余风险 / 台账指针 |

### P2 全新交付
同 P1，去掉阶段 1；若用户有参考项目但没给路径，先要参考（这是唯一允许的提问点之一），没有则直接进规划。

### P3 修复
`debug-and-refactor` 定位修复 → 相关回归 → 改动面大于一个文件时补 `ponytail-review` → 交付。不建全套台账，一个简短的"症状→根因→修复→验证"四行记录即可。

### P4 增量
规划 → 开发（ponytail 常驻）→ 测试/审查（改动大才加：前端改动加 `frontend-review-squad`，页面级验收走 `ui-acceptance`）→ 交付。若项目已有 `docs/project-map/`，先读它定位改动影响面；没有且预计改动跨 3+ 模块，先问用户要不要走一次体检测绘。

## 流水线台账（状态外置）

每个进流水线的任务在目标仓库建 `docs/pipeline/<task-slug>.md`：

```markdown
# Pipeline: <任务一句话>
类型: P1 倒模交付 ｜ 参考: <repo/路径> ｜ 状态: 🔄 进行中
| 阶段 | 状态 | 出场条件核验 | 产物指针 |
|---|---|---|---|
| 1 测绘 | ✅ | 台账闭环 ✅ | docs/project-map/ |
| 2 规划 | ✅ | 阶梯排序 ✅ | docs/pipeline/x-tasks.md |
| 3 开发 | 🔄 | 3/7 项 | docs/pipeline/x-tasks.md |
| 4 调试 | ⬜ | — | — |
```

阶段状态只有四种：`⬜ 未开始` / `🔄 进行中` / `✅ 出场条件已核验` / `⛔ 受阻（原因 + 需要用户拍板的问题）`。

**断点续跑协议**：新会话第一件事读台账 → 从第一个非 ✅ 阶段继续 → 已完成阶段不重跑，只抽查产物文件还在 → 向用户报一句"流水线从阶段 N 继续"即开工。每完成一个阶段立刻落盘。

## 阶段失败分支（出场条件不满足时）

| 失败信号 | 处理 |
|---|---|
| 子 skill 产物缺失（地图/清单/delete-list 没落盘） | **停在当前阶段**；先让对应 skill 重跑或补落盘；台账状态保持 `🔄`，不进入下一阶段 |
| 出场条件无法在合理时间内满足（缺参考、缺环境、缺权限） | 台账标 `⛔ 受阻`，写清阻塞点 + 需要用户拍板的具体问题；不擅自跳过阶段 |
| 执行中发现规划遗漏，已做产物需返工 | 回到规划阶段，把遗漏写入任务清单；受影响阶段重开，后续阶段不复用旧产物 |
| 用户中途改范围/目标 | 更新任务类型判定；如果 P1/P2/P4 被改成 P3 或反之，台账记「换线」，按新线重排阶段 |
| 子 skill 互相冲突（一个要求删、一个要求留） | **停下问用户**，把两边证据并排列出；不自行裁决 |

**🔴 CHECKPOINT · 阶段门禁**：每个阶段结束时，台账必须写清「产物指针 + 出场条件核验结果」。没有这两项 = 阶段未完成。

## 编排纪律

- **一次只推进一个阶段**；阶段内你可以完全自主，**阶段之间必须核验出场条件**——"感觉差不多"不是核验。
- **官方镜像路由**（交付物/设备类阶段按需加载）：文档交付 → `docx`/`pdf`/`pptx`/`xlsx`；移动端验证 → 仅在 `android-emulator` / `ios-simulator` 插件可用时加载 `android-dev`/`ios-dev`（两者已归档，未启用则标注 `⛔ 受阻`）；浏览器/桌面自动化验证 → `control-browser`/`computer-use`；ZCode 资源装载异常 → `zcode-configuration-guide` + 对应 `diagnosing-*`；写新 skill → `skill-creator`。
- 子 skill 的产出一律落盘（cartographer 的地图、review 的 delete-list、任务清单），你的台账只存指针，不复制内容。
- **升级决策停下来问**：改架构、删用户没让删的东西、超出原始范围、P3 修出 P2 的规模——其余全部自己走。
- **用户点名某个 skill 时绕过流水线**，直接执行点名诉求；路由器是默认路径，不是关卡。
- 汇报节奏：每进一个新阶段报一行"→ 阶段 N（skill X），出场条件 Y"；不要长篇大论。

## Windows 本地服务 / 桌面交付补充门禁

当交付物包含 Windows exe、常驻网关、看门狗或桌面壳，P3/P4 的“相关回归”升级为下面五项；缺一项都不算可交付：

1. **构建口径固定**：桌面端 GUI 发布必须带 `-H=windowsgui`；服务端 CLI 保持 Console 子系统，两个目标不能混用一个构建命令。
2. **PE 产物核验**：直接读部署 exe 的 PE `Subsystem`，不能只看文件名、manifest 或构建日志；桌面端=2，服务端=3。
3. **部署物一致性**：对源码构建产物和运行中的部署 exe 做 SHA256 对比，确认运行值不是旧文件。
4. **进程生命周期**：连续执行启动、停止、再启动；检查同端口残留、同名旧进程、看门狗抢拉起、子进程 `conhost`。停止顺序必须先阻断看门狗，再停服务，最后释放端口租约。
5. **发布动作授权**：提交/tag/push 是外部状态变更，用户未明确说“推送/发布”时只允许本地构建与验证，不得先推再解释；若远程 tag 已存在，不擅自覆盖。

## 反例黑名单（不要这么做）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| 1 | 开一个 `docs/pipeline/*.md` 就宣布「进了流水线」 | 台账不是推进；没有产物指针和门禁核验，只是形式主义 | 第一个阶段也要有产物，台账写指针 |
| 2 | 阶段还没过出场条件就继续写代码 | 后一阶段会建立在错误产物上，返工成本按阶段数放大 | 停在当前阶段，补产物或标 `⛔` |
| 3 | 把「感觉差不多」当门禁 | 没有可核验证据，无法断点续跑 | 写「产物路径 + 通过/失败项」 |
| 4 | 子 skill 的结论只留在上下文里 | 新会话接不上，等于没做 | 一律落盘，台账只存指针 |
| 5 | 用户说「修一下」却升级成全量重做 | 擅自扩大范围，违背 P3 > P1 > P4 > P2 | 按最轻线走，扩范围前问用户 |
| 6 | 多个子 skill 意见冲突时自己拍板 | 冲突通常意味着需求/约束没对齐，自行裁决会掩盖问题 | 停下，列双方证据，让用户选 |
