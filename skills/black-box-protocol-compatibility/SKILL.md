# 黑盒客户端协议兼容工程

这不是“猜 API”技能，而是“把官方客户端当作协议规范”的技能。适用于任何黑盒客户端，不限于 AI Agent：

- AI Agent / IDE / 编码助手（Codex、Claude Code、ZCode、Cursor、Qoder、Cline 等）
- 桌面软件、Electron / Tauri / WebView 应用
- 浏览器插件、移动端 App、小程序
- CLI、游戏启动器、下载器、同步客户端
- 任何“文档很少、只有官方客户端能用、普通 HTTP 请求会被拒绝”的上游

## 什么时候用

- 普通 OpenAI / REST 请求打不通，但官方客户端正常
- 上游返回 `405 unusual activity`、`request illegal`、`request has been blocked`、`403`、`3012`
- 需要复刻登录态、设备 ID、会话 ID、签名、时间戳、nonce、指纹
- 需要区分认证失败、无权益、配额耗尽、风控封禁、请求形状错误、上游故障
- 需要把某个客户端能力接进自己的网关、代理、自动化或兼容层
- 需要判断“只差一个 header”还是“整个请求模型都不对”

## 核心原则

### 1. 官方客户端是唯一事实源

文档、SDK、接口清单都可能滞后。优先级：

> 官方客户端真实请求 > 官方客户端产物 / 本地配置 / 日志 > 源码推断 > 文档 > 猜测

不要先假设它是标准 API。先确认它到底是什么客户端协议。

### 2. 正向兼容 + 负向兼容

不仅要补“官方客户端发了什么”，还要查“官方客户端没发什么”。

负向兼容经常是成败关键：

- agent 自带的 `anthropic-beta`、`x-stainless-*`、`x-app` 不能透传
- 浏览器请求头不能出现在桌面客户端协议里
- 多一个 system block、少一个 `metadata` 字段都可能被拒
- 查询参数、Content-Length、Accept-Encoding 也可能参与判定

### 3. 认证、权益、请求形状、风控是四件事

不要把 4xx 都当“重试”：

- `401`：登录态失效 / 凭据不被接受
- `403` / `405` / `3012`：风控、请求不像官方客户端、网络或账号被封
- `1113` / `1005`：无套餐 / 无资源包 / 配额超限
- `429`：限流或额度耗尽
- `5xx`：上游临时故障

先分类，再决定换号、重试、降级、停止还是让用户重新登录。

### 4. 身份和状态必须稳定

重点检查：

- 设备 ID：是否稳定、是否来自官方客户端、是否每请求随机
- 会话 ID：是否每轮保持、是否与 metadata 对齐
- 账号 ID / 项目 ID / 团队 ID：是否参与路由或缓存
- 时区、语言、平台、客户端版本：是否影响风控或缓存
- 登录态文件：是否会被官方客户端轮换、是否可刷新

### 5. 证据不足时停止猜

同一类假设连续失败 2 次，必须换证据源：

- 不再加 header
- 不再换 endpoint
- 不再重试
- 去抓官方客户端真实请求、读客户端产物、看本地日志、做最小对照

## 工作流

### 阶段 0：边界与目标

先写清楚：

- 目标客户端与版本
- 目标能力（登录、模型列表、对话、上传、支付、任务等）
- 授权范围（仅本人账号 / 本机 / 私有环境）
- 成功标准（一次请求成功不算，要能稳定复用）
- 不可接受的风险（账号封禁、验证码、不可逆操作）

只做授权范围内的兼容性研究，不把绕过风控包装成通用能力。

### 阶段 1：收集证据

至少收集以下证据：

1. 客户端版本、安装目录、更新渠道
2. 安装包 / asar / 插件包 / 前端 chunk / source map
3. 本地配置、缓存、登录态文件、设备 ID 文件
4. 官方客户端发出的真实请求：URL、method、query、headers、body
5. 成功响应、失败响应、SSE 流、错误码
6. 同一操作的多次样本，确认哪些字段稳定、哪些随机
7. 对照样本：普通请求失败、官方请求成功

证据记录模板：

```text
[证据编号] 时间 / 客户端版本 / 操作
- 来源：抓包 / 本地文件 / 日志 / 安装包 / 文档
- 请求：method URL query
- 关键 headers：
- body 结构：
- 身份字段：
- 响应 / 错误码：
- 结论：
```

### 阶段 2：建立协议矩阵

不要只记一个 curl。建立矩阵：

| 维度 | 要确认的内容 |
|---|---|
| 传输 | HTTP/1.1、HTTP/2、WebSocket、SSE、IPC、gRPC、WebView bridge |
| 入口 | 域名、路径、query、版本前缀、区域站点 |
| 认证 | cookie、Bearer、API key、JWT、签名、OAuth、设备绑定 |
| Headers | 全量 header，标注“必须有 / 可省略 / 绝不能有” |
| Body | 字段、嵌套结构、顺序敏感项、system / context / metadata |
| 身份 | device_id、session_id、account_id、project_id、team_id |
| 状态 | 登录态、刷新机制、过期时间、冷却、额度 |
| 时序 | 日期、时间戳、nonce、重放窗口、请求顺序 |
| 环境 | OS、架构、语言、时区、客户端版本、UA |
| 错误 | 业务码、HTTP 状态、错误文本、可重试性 |

### 阶段 3：做差异对照

把“当前请求”和“官方请求”逐项 diff：

1. URL / method / query
2. header 集合：缺什么、多什么、值差在哪
3. body 顶层字段
4. 嵌套结构：system block 数量、消息顺序、metadata
5. 身份字段：device / session / account
6. 时序字段：日期、nonce、时间戳
7. 传输层：压缩、编码、连接复用、TLS 指纹（如确有必要）

优先验证“多发了什么”，再验证“少发了什么”。

### 阶段 4：权益与路由模型

如果上游按账号 / 套餐 / 赠送额度路由，必须单独建模：

- 账号自己的套餐
- 团队席位
- 免费 / 赠送 / 试用额度
- 按模型区分的权益
- 额度桶、过期时间、剩余量
- 某模型该走哪个额度、失败后能否回退

不要用“账号健康”代替“该模型可用”。

### 阶段 5：错误分类

建立错误表，至少包含：

| 现象 | 可能原因 | 动作 |
|---|---|---|
| 401 | 登录态失效 / 凭据错误 | 重新登录或换号 |
| 403 / 405 / 3012 | 风控 / 请求形状不对 / 网络被封 | 停止重试，对照官方请求 |
| 1113 / 1005 | 无套餐 / 无资源包 / 配额超限 | 换额度或换号 |
| 429 | 限流 / 额度耗尽 | 退避、换号或停止 |
| 5xx | 上游故障 | 有限重试 |
| 空流 / 半截流 | 协议转换或上游中断 | 保留原始响应，单独排查 |

### 阶段 6：实现适配层

推荐分层：

```text
入站协议
  -> 归一化请求模型
  -> 账号 / 权益 / 路由选择
  -> 客户端协议 profile
  -> 上游请求
  -> 上游响应 / SSE
  -> 回程协议转换
```

纪律：

- 协议细节集中到 profile，不散落在业务代码
- 版本号、UA、OS、语言、时区可配置
- 保留原始请求 / 原始响应用于排障
- 不在流式响应上做不必要的缓冲
- 所有错误码映射有测试
- 账号切换不改变会话身份语义

### 阶段 7：契约测试

至少四类测试：

1. **正样本**：官方客户端真实请求 fixture 能通过
2. **负样本**：多一个 header、少一个 system block、错 session id 必须失败或被识别
3. **错误映射**：401 / 403 / 405 / 429 / 1113 / 1005 / 5xx 分类正确
4. **流转换**：SSE 事件、tool call、thinking、usage 不丢

一次成功只能证明“当时能通”，fixture 才能证明“以后不容易坏”。

### 阶段 8：上线与观测

- 先小流量验证
- 记录客户端版本、协议 profile 版本、错误码分布
- 上游改版时能快速定位是认证、请求形状、权益还是风控变化
- 保留回滚开关
- 不把临时绕过写成永久默认

## 快速判断：是“差一个参数”还是“协议不对”

出现以下信号，优先怀疑协议模型不对：

- 官方客户端正常，普通请求稳定 405 / 403
- 换 token 无效
- 加 header 偶尔成功、随后又失败
- 请求体越像普通 API 越容易被拒
- 错误码是业务码而不是标准 HTTP 语义
- 同一账号在官方客户端可用，在反代不可用
- 上游要求 captcha、设备绑定、客户端指纹

## 输出物

一个合格的协议兼容工程至少留下：

1. 协议矩阵
2. 证据清单
3. 错误码表
4. 客户端协议 profile
5. 适配层代码
6. fixture 与契约测试
7. 版本兼容说明
8. 回滚与观测方案

## 与其他 skill 的关系

- 先用 `web-app-capability-mining` 找全能力面
- 用本 skill 把目标能力复刻成协议适配层
- 遇到“改了没生效 / 跑的是旧产物 / 端口被占”用 `debug-and-refactor`
- Agent 自己反复试错、循环卡死时用 `agent-introspection-debugging`
- 经验稳定后由 `project-memory-sculptor` 沉淀到项目 `AGENTS.md`

## 停止条件

出现以下情况，停止并报告，不要继续试：

- 需要验证码 / 真人验证 / 不可逆账号操作
- 账号已被风控，继续请求只会加重
- 连续两次同类假设失败且没有新证据
- 只能靠伪造他人身份或未授权凭据才能继续
- 上游明确禁止且没有授权范围
