# 项目测绘师 (Project Cartographer)

> **定位（先对齐预期）**：本 skill 做的是**能力 / 结构探查**——有什么、在哪、暴露没暴露、谁调用谁。
> 它**不负责猎捕缺陷**，尤其不擅长「某个状态下入口不可达 / 不可发现」这类**状态轴**问题
> （实证：无症状态盲测两轮都没抓到，一旦给出症状立刻命中）。要查 bug / 做审查，走
> `frontend-review-squad`（已包含本 skill 的闭环映射能力）或 `debug-and-refactor`（Part E 的 E12/E13）。


你要做的事情本质上只有一件：**画一张没有多余出口的迷宫地图**。

- 每个路口都有指示牌：这是什么、里面有什么、通向哪里、从哪里来。
- 死胡同不是断头路，也有牌："此路不通"+ 原因 + 回头路。
- 绝不允许存在一条没被标注的岔路——发现即入账，入账必销账。
- 水一样流动：看到按钮就顺着它流过去，到了新地方发现新按钮，再分别流下去，直到流不动（UI 叶子）或流进后端某个具体函数为止。

这套地图有两种用法：**探索参考项目**（看清别人的功能层级和 UI/UX，供自己倒模）和**梳理自己的项目**（暴露前后端缺口）。

## 核心法则一：闭环（台账）

一切围绕一份**台账**（traversal ledger）运转。这是整个技能的发动机，绝不能省略。

每个发现的节点（路由、控制器、服务、页面、组件、交互点……）必须出现在台账里，且状态只有三种：

1. `✅ 已测绘` — 已写出指示牌，所有子节点已入账
2. `⛔ 死胡同` — 是叶子或不可再深入，已注明原因和回头路
3. `🚧 待测绘` — 已发现但还没走到

**完成条件只有一个：台账里没有任何 `🚧 待测绘`。** 台账不清零，地图就不算画完，不要提前收工。中途确实走不完（项目太大、超时）时，必须如实保留 `🚧` 项并在概览中说明"本图未闭环，还剩 N 个路口"，绝不能假装画完了。

### 断点续测协议（中断/压缩后怎么接上）

长任务必然跨会话或经历上下文压缩。恢复规程：

1. 新会话第一件事：读 `docs/project-map/_ledger.md`。**台账就是任务队列**——恢复执行 = 挑下一个 `🚧`。
2. `✅` 一律不重测；`⛔` 不重开（除非用户点名）。只做 `🚧`。
3. 续测前抽查一个已 ✅ 节点，核对其指示牌与当前代码是否仍相符（代码可能已变更）；不符就把该节点降回 `🚧` 并注明"代码变更，需重测"。
4. 台账不存在 → 从 Step 0 从头建图；台账存在但 `00-overview.md` 缺失 → 先补概览再继续。
5. **每销一账立刻落盘**（台账与指示牌同写），保证任何时刻中断最多损失一步。
6. 续跑时不需要向用户复述全部历史——读台账、报一句"从 X 继续，剩 N 个 🚧"即开工。

## 核心法则二：水流（跟着交互走）

分层扫荡给出"有哪些层"，但**功能几何**要靠水流追踪：从每个交互点（按钮、右键项、输入、拖拽、快捷键）出发，顺着它真实流动——

```
交互点 → 事件处理 → emit/路由跳转 → 新界面/弹层 →（发现新交互点，全部入账）
       → store 动作 → composable → API 门面 → 传输层 → 后端具体函数
```

终止条件只有两种：**UI 叶子**（纯展示，无出站调用）或**后端具体函数**（IPC/RPC/端点名）。到函数为止就算"接上了地气"，不要停在中间层就宣布走完。流经的每一跳都要记 file:line 证据，不许脑补链路。

> **静态联通 ≠ 运行时闭环。** 链路走到后端函数名、curl 也是 200，只说明"代码里这条路存在"，**不代表浏览器里点得动**。真实教训：opscore「日志」按钮，`fetchLog → /pod/log → 后端` 全链路静态通 + curl ok:True，但浏览器实际点击无反应——根因在渲染层（弹层未挂载/回调触发但无落点），单人看代码抓不到。所以**凡交互点（按钮/右键/输入/弹层）测绘，走完静态流后默认挂 `🚧 待运行时验证`**，命中易漏特征（有异步、落点与交互不在一处、用户报过"点了没反应"）时必须做运行时实测。方法读 `references/runtime-verify.md`：**先后端契约直探（HTTP/WS 最小客户端把"后端正不正常"独立出来，别再绕 UI 猜链条），再浏览器三线对账**；走 WS 的交互点（日志跟随/终端/事件流）必须用独立 WS 探针打帧归因，浏览器三线正常 ≠ WS 帧层无异常。台账里 `✅ 已测绘` 的交互点若没标注"已实测"，概览需如实说明。**稳态点过 ≠ 中间态不炸**：交互点渲染依赖异步数据时，还要在加载中/切换重渲染窗口/错误恢复后各点一遍（瞬态验证），右键"空菜单一条线"、undefined prop 崩溃白屏这类 bug 只在中间态出现。

## 核心法则三：局部树（3~4 层封顶）

任何一棵树文档**最多 3~4 层**。要再深时，不继续展开，而是把当前节点立为新的**子树根**，单独成文档，用编号寻址（如 `DBX-02A`、`DBX-02A-01`），父子文档互相链接。整份地图因此是一组可导航的局部树组成的**网格**，而不是一棵两千节点的巨树——所有树拼起来仍覆盖全部真实源码。

四类产出各答一个问题：

| 型 | 产出 | 回答 | 何时做 |
|---|---|---|---|
| A | 总体架构树（1 份，5~6 大分支） | 项目是什么结构？ | 必做 |
| B | 子树文档（按需递归展开，每棵 3~4 层） | 这个模块由哪些源码组成？ | 必做 |
| C | 功能流（一次操作穿全系统） | 代码怎么跑？ | 必做 |
| D | 特性映射表（特性↔组件↔store↔composable↔API） | 一个功能落在哪些层？ | 必做 |
| **E1** | **实现档案** | **它是怎么做出来的？** | 值得倒模 / 值得体检的关键功能 |
| **E2** | **品质档案** | **它为什么好用、好看、快？** | 值得倒模 / 用户问“为什么它好用” |
| **F** | **系统语义档案** | **数据怎么流转、权限怎么判、状态以谁为准？** | 跨模块功能 / 有写操作 / 有多角色 / 多副本状态 |

目录树与功能流**分开成图**、通过子树编号**交叉引用**：从 B 里任何一跳可以跳进 C，从 C 任何一端可以反查 B。

**A–D 是结构，E/F 是质量与语义。结构闭环只证明“通着”，不证明“好”和“对”。**

| | 回答 | 证据来源 | 详细方法 |
|---|---|---|---|
| **E1 实现档案** | 内部机制：业务规则、数据模型、技术取舍、关键路径 | 读源码 + file:line | `references/implementation-probe.md` |
| **E2 品质档案** | 涌现品质：视觉量测、交互时序、性能规模 | **必须运行**，截图/录屏/实测 | `references/quality-probe.md` |
| **F 系统语义档案** | 数据生命周期、权限与身份、状态一致性 | 跨层读 + 运行验证 | `references/state-permission-probe.md` |

**三者的区别一句话说清**：

- E1 读代码就知道（它怎么写的）
- E2 必须跑起来才知道（它为什么好）
- F 必须横切才知道（它在什么前提下是对的）

**硬判据**：E2 没有运行证据 → 一律 `⚠️ 未验证`；F 指不出唯一事实源 → `❓ 事实源不明`。

## 核心法则四：观测边界（不把"没找到"当成"不存在"）

地图的空白会被读者理解成"这里没有东西"，而不是"这里没查"。这是本 skill 最危险的系统性错误：**观测不足 → 直接判定不存在 → 读者当真 → 倒模时删掉真功能 / 误判结构残缺。**

所以：**只报告"发现了什么"和"没找到什么"，不报告"不存在"。**

### 三种证据等级

| 等级 | 含义 | 允许的表述 |
|---|---|---|
| **已证实** | 追到 IO / 渲染 / 明确契约，有 file:line | 可以下结论 |
| **未找到** | 搜索过、没命中，但未排除替代解释 | 只能写"未找到"，附搜索范围 |
| **无法判定** | 静态不可判断（运行时、外部系统、时间触发） | 标 `❓`，写清为什么判不了 + 怎么才能判 |

### 任何否定式判定必须附三样

`未消费` / `死胡同` / `僵尸` / `悬空` / `未暴露` / `死代码` —— 这些标签自带结论，必须同时给出：

1. **搜索范围**：grep 了什么模式、扫了哪些目录、排除了什么文件
2. **已排除的替代解释**（按类型选，见下表）
3. **确认方式**：跑什么命令、查什么文档、问谁能真正确认

三样缺一，标签降级为 `❓ 未确认`，**不许用结论性符号**。

### 七类必须先排除的替代解释

| 替代解释 | 典型形态 | 怎么排除 |
|---|---|---|
| **时间触发** | `expires_at`、`next_run`、定时清理 | 找调度器（cron / scheduler / ticker / setInterval） |
| **事件触发** | 状态机迁移、消息订阅、webhook 回调 | 找事件注册（subscribe / on / emit / listen） |
| **跨仓消费** | API 响应字段、事件 payload、导出格式、下游服务 | 找出站契约（OpenAPI / 类型定义 / 文档） |
| **动态调用** | 反射、`getattr`、字符串映射、依赖注入容器 | 找字符串常量与注册表（不是直接调用） |
| **框架约定** | 生命周期钩子、`__init__`、装饰器注册、路由约定 | 对照框架文档确认调用时机 |
| **条件编译 / 配置驱动** | `#ifdef`、feature flag、插件清单、环境分支 | 找构建配置与开关定义 |
| **外部使用者** | 公开库 API、给第三方的接口、脚本入口 | 查文档、导出清单、CLI 定义 |

**判死前必须逐条过一遍这张表。** 过完仍无法解释，才可以下结论，并在指示牌上写明"已排除以上七类"。

### 视觉强度与置信度必须匹配

`⛔` `🕳️` `👻` 这类符号在渲染上很强，读者会当成确定结论。所以：

- 证据等级 = 已证实 → 才允许用强符号
- 证据等级 = 未找到 / 无法判定 → 只能用 `❓`，并附三样

不要让一个"我没搜到"用 `⛔` 的视觉权重呈现。

## 工作流程

### Step 0 — 建图（深度是路由出来的，不是默认全量硬上）

1. **先判任务状态定深度**：目标项目已有本 skill 产出的地图且代码变动不大 → **增量续测**（走断点续测协议：读台账 + 漂移抽查）；用户声明熟悉某模块或只要某几个模块 → **模块级测绘**（边界外标 `🚧`）；greenfield / 全新项目 / 用户要全量 → **全量测绘**。路由错了随时换档，台账记一笔。
2. 确认测绘对象（参考项目 or 自己的项目）和输出目录，默认 `<项目>/docs/project-map/`。
3. 快速侦察项目技术栈：读 package.json / requirements.txt / 入口文件 / 路由注册处，判断后端框架、前端框架、两者如何通信（REST / WebSocket / RPC）。
4. 建立台账文件 `docs/project-map/_ledger.md`，把第一层节点入账。

### Step 1 — 分层扫荡（广度优先，逐层销账）

后端一条线、前端一条线，分别向下扫：

- **后端**：API 路由 → 控制器/Handler → 服务层 → 数据模型/存储。每一层的孩子全部入账后再往下一层。仓库里没有后端源码（纯客户端项目）时，后端线测绘**应用消费的 API 面**：封装层、端点清单、类型契约、Mock/替身——这些就是这张图的后端，并在概览里注明"真实后端在仓库外"。
- **前端**：路由/菜单 → 页面 → 布局 → 组件 → 交互点（按钮、表格、输入框、列表、图表、示波器、右键菜单、弹窗）。交互点就是前端的最深一层，它们是"路面的尽头"，全部按死胡同处理但必须标注它们触发了哪个后端调用。
- **形态普查（前端表面节点专属）**：页面/面板/弹窗这些"有脸面"的节点，指示牌加第六行**形态牌**——布局骨架 + 控件谱 + 交互语法 + 形态指纹。拓扑回答"在哪"、流回答"怎么跑"，形态牌回答"长什么样、摸着什么手感"。**布局骨架要含 3.5 布局缺口探查**（grid/flex 子控件可收缩性，防"弹窗溢出/内容放不下"），因为形态牌是"倒模带回新模板"的载体——只抄分布不查子控件可收缩性，倒回来的模板会带旧写法。提取方法读 `references/morphology-probe.md`。

扫描节奏：每测绘完一个节点，**立刻**写该节点的指示牌并更新台账状态，再走向下一个 `🚧`。不要攒到最后一起写——攒账就会烂账。

具体到某类框架（Express / FastAPI / Spring / Vue / React / Qt / 嵌入式 Web 等）怎么找入口和层级，读 `references/sweep-strategy.md`。

### Step 2 — 水流追踪（法则二的执行）

分层扫荡画出"骨架"后，对每个交互点放水：

1. 从台账里任选一个交互点，顺着事件链走：`@click/命令 → 处理函数 → emit/导航 → 落点界面`。落点如果是新界面/弹层，把其中**新出现的交互点全部入账**，继续放水。
2. 写侧继续流：`store 动作 → composable → API 门面 → 传输层（invoke/fetch）→ 后端函数名`，到**具体函数名**为止。
3. 每条流记录成 C 型功能流文档（垂直链 + 每跳 file:line）。同一个模块的交互点共享后段时，后段只写一次、其余引用，避免复制粘贴。
4. 流动中发现的任何新节点（中间件、事件总线、缓存层）回填台账。

**判叶子标准（四级，不轻易标 ⛔）**：链停在"没有出站调用"时，先排除四种情况再下结论：

| 情况 | 判据 | 标记 |
|---|---|---|
| **真叶子** | 纯计算/纯展示，且确认无外部调用者 | `⛔ 叶子` |
| **间接调用** | 反射、装饰器注册、框架生命周期钩子、依赖注入 | `🔗 间接调用` |
| **外部使用者** | 公开 API、给第三方的接口、CLI/脚本入口 | `🌐 外部使用` |
| **未确认** | 没排除完 | `❓ 未确认` |

标 `⛔` 前必须逐条排除后三种，并在指示牌上写明"已排除：反射 / 框架钩子 / 外部调用"。**停在"还没到后端函数就不想走了"仍然是违规**——要么流到底，要么如实标 `🚧`。

**数据层顺带做僵尸核对**：水流走到任何 schema/结构体字段时，顺带确认三条边完备——有写点、有读点、读点砸到真副作用（IO 或渲染分支）。字段若被"搬运给下一个结构体"而已，不算消费，继续追直到 IO 或回显。核对方法见 `references/sweep-strategy.md`。这不用单独开一条流，但在台账节点指示牌的"出口/死胡同"里要给数据字段落账，否则数据模型成了地图的盲区——`log_sources.follow` 那种"schema 自洽但消费缺失"的假功能就漏了。

UI 布局类问题（出视口/留白不对称/未贴合），用户指出具体现象后按 `references/ui-layout-debug-method.md` 四招必达（高度链/几何量化/样式考古/统一度量），现象→路径映射表在文首。

**锚点因生态而异**。每种语言/框架都有三类显眼标记可顺藤摸瓜：注册表标记（路由/菜单/命令注册处，列出全部入口）、流转标记（emit/dispatch/channel/inject，把链走通）、终止标记（fetch/sql/exec/FFI，见到底了）。目标项目是什么生态，先读 `references/trace-markers.md` 选对该锚点再放水——Vue 的 `@click/emit`、React 的 `onClick/dispatch`、Spring 的 `@GetMapping`、Go 的 `r.GET`、Rust 的 `#[tauri::command]`、gRPC 的 `rpc`，本质是同一件事：**顺着语言自己暴露的钩子逐节点探查**。

### Step 3 — 双向映射

画完两条线后，生成映射矩阵 `04-mapping.md`：每行一个后端能力，标注哪些前端交互点使用它；反过来每个前端交互点必须能回溯到至少一个后端调用。这是"闭环"在前端与后端之间的体现：

- 后端有功能、前端没有找到入口 → 先标 `❓ 未见入口`，不是 `🕳️ 未暴露`
- 前端有按钮、后端没找到对应实现 → 先标 `❓ 未见实现`，不是 `🪝 悬空调用`

**命名即结论，所以这里的标签必须是问句不是判决。** 下结论前必须排除：

| 疑问 | 必须先排除 |
|---|---|
| `❓ 未见入口` 能否升级为 `🕳️ 未暴露` | ① 是否被 feature flag / 权限开关关闭 ② 是否给第三方或脚本用（本仓无 UI 是正常的）③ 是否通过菜单/命令面板/快捷键等隐式入口进入 ④ 是否是内部调试接口 |
| `❓ 未见实现` 能否升级为 `🪝 悬空调用` | ① URL 是否动态拼接（模板字符串/变量）② 是否指向仓库外服务（反代/网关/微服务）③ 路由是否在配置或插件里注册 ④ 是否用 SDK/生成客户端间接调用 |

三种情况都排除后，才可用 `🕳️` / `🪝`，并在条目上写"已排除：flag / 外部 / 动态 / 配置"。

这两类仍是梳理自己项目时最值钱的发现——但**要先证明'真的没有'，才值得修**。

### Step 4 — 闭环验收（人工清单 + 机械凭证 + 理解验收）

收工前自查：

- [ ] 台账无 `🚧`（含 `🚧 待运行时验证`；交互点未经浏览器实测即标 ✅ = 违规，降回 🚧）
- [ ] 每个节点的"出口"链接都指向真实存在的子节点，"父节点"回链也成立（无悬空引用）
- [ ] 每个死胡同都写了原因
- [ ] 映射矩阵里没有没被解释的 `🕳️` 和 `🪝`（要么修复，要么在概览里明确列出）
- [ ] 每条功能流都到达了终止条件（UI 叶子或后端函数名），无中途弃流
- [ ] 抽查交互点（含用户报过"点了没反应"的）：有运行时实测记录（Console/Network/DOM 三线），或不适用并写明原因
- [ ] **交互点清单按「载体」穷尽**（显式控件 / 表内手势·右键 / **拖拽与放置** / 键盘 / **触摸与指针** / **剪贴板** / **编辑器与画布** / **图表交互** / 隐式入口），不是按"看起来像入口"穷尽 —— 完整载体表见 `references/sweep-strategy.md`「交互点载体清单」
- [ ] **交互点 × 状态边界矩阵已出**（正常 / 零行·空结果 / 出错 / 门控未开·默认折叠 / 超宽超长），每个组合答"在 DOM 里吗 / 够得着吗 / 动作还成立吗"；**任何"未验证"必须进结论区的缺口清单，并区分两类**：`🚧 环境不可达`（附实测命令与输出证明构造不出来）vs `❌ 未执行`（能构造但没跑）。前者记风险，后者记欠债——**不许混为一谈**，也不许只写在末尾〈未覆盖〉段里 → `references/runtime-verify.md` 二·七
- [ ] 没有任何一棵树文档超过 4 层——超了就拆子树
- [ ] **品质结论全部有运行证据**：E2 里任何“流畅/好看/快”的描述都附了量测值或实测数据；没有的一律 `⚠️ 未验证`
- [ ] **系统语义三项成对核对过**：数据+权限、权限+状态、状态+数据，不只看单项
- [ ] **每个功能能指出唯一事实源**：指不出的标 `❓ 事实源不明`，不算完成
- [ ] **字段消费已按四态核对**（`references/sweep-strategy.md` 的"字段消费核对"）：每个字段标 `✅ 已消费` / `⏳ 条件消费` / `↗️ 跨仓消费` / `❓ 未确认` / `👻 僵尸字段`。判 `👻` 前必须已排除时间触发、事件触发、跨仓、动态反射、批量后台五种消费方式；排除不完的只能标 `❓`

**机械对账（receipt 思路：每项留下命令与输出，写进 `_receipt.md`，可被任何人复跑）**：

- [ ] **数字断言对账（含口径声明）**：地图里写的每个数字重新跑一遍 grep/wc，输出贴进凭证；**同时写明 grep 口径**——是否包含注释、字符串字面量、测试文件、.gitignore 之外的文件。三个口径数出来的结果可能差一倍，不声明口径的数字是假的。
- [ ] **file:line 抽查**：随机抽 3~5 处引用，验证该行确实是所声称的符号。抽中即全体的置信度代理。
- [ ] **链接完整性**：所有 `[[节点]]` 与相对路径引用可解析；节点数与各子树文件数对账。
- [ ] **注册表对账**：对声称"全覆盖"的注册表（枚举/菜单工厂/命令表），重跑枚举命令数一遍——33 是数出来的，不是印象。

**理解验收（完成定义 = 台账清零 + 用户答得上）**：出 **费曼自测 5 题**，每题标注回链的地图章节（格式 `Q3 → 04-mapping.md 判定标准`），附进 `_receipt.md` 或走查文档。题要打地图的主轴（单点出口为什么存在、新数据源接几处、判定标准是什么），不打细枝末节。用户答不上的题号 = 地图对应章节要加密重讲的地方。

### Step 5 — 产出

输出到 `docs/project-map/`，按四型组织（编号 `<项目缩写>-<两位数>`，子树用字母后缀 `<02A>`，再下层 `<02A-01>`）：

| 文件 | 型 | 内容 |
|---|---|---|
| `_ledger.md` | — | 台账：所有节点 + 状态，地图的"总账" |

## 节点指示牌格式

每个节点的牌面固定五项，写法示例：

```markdown
### 2.3 设备管理  `GET /api/devices`
> 父节点：[[2. 设备中心]] ｜ 状态：✅ 已测绘 ｜ 前端入口：[[F-3 设备列表页]]

**这是什么**：设备的增删改查与状态轮询入口。
**里面有什么**：列表查询、单台详情、批量下发指令三个能力。
**出口**：2.3.1 指令下发（→ 走）｜2.3.2 固件升级（→ 走）
**死胡同**：2.3.3 日志导出（⛔ 后端只留了接口签名，未实现，回头路 → 2.3）
**关联前端**：F-3 的表格列 "状态" 点击即调 GET /api/devices/:id
**形态**：纵向三分（工具栏/列表/确认层）· 控件谱：列表×1 Chip×4 Sheet×2 · 语法：@click 长按·搜索即时过滤 · 指纹：浏览器型（→ morphology-probe.md）
```

死胡同的牌至少要说清两件事：**为什么是死胡同**（叶子/未实现/占位符/被废弃）和**回头路在哪**（链接到最近的活岔口）。让读地图的人走到头也不会卡在墙面前。

节点编号建议用"层号.序号"（后端 `B-`，前端 `F-`）， wikilink `[[...]]` 或相对路径链接均可，但要保证双向可点。

## 漏检复盘协议（"目标项目还有 X，我们地图上没有"时必走）

倒模 ≠ 完备。扫荡是注册表驱动的：不在任何注册表（路由表/菜单工厂/命令清单）里的功能天生隐形。所以每次用户指出遗漏，走四步，**不许只把功能补进地图就完事**：

1. **定向补测**：按 `references/miss-hunt.md` 的手法（文档先行 / i18n 词表反查 / 入口普查 / 配置资产扫描 / 孤儿函数反向核查 / 枚举值穷举 / 拼装点追查）找到 X 的实现，落一份带 file:line 的微型档案入台账。不重开全量测绘。
2. **根因归类**：对照 miss-hunt 的漏因表，回答"系统性扫荡为什么没抓到"。最高频的答案不是"不仔细"，而是**词汇错位**（它内部叫的名字和你嘴里的不一样）和**无 UI 入口**（我们只扫了交互点，它藏在 store/服务层）。
3. **手法沉淀**：抓到 X 的手法若可复用（新锚点、新扫荡步骤、新漏因类别），写进本 skill 的 references——**每次漏检都必须让下次更难漏**。沉淀格式：一句话触发时机 + 可执行的 grep/操作 + 归档到哪份参考。先例：`structure-mechanism-probe.md` 就是一次漏检复盘的产物（缺口在台账躺了几个迭代，因为没人记实现方式）；`runtime-verify.md` 是另一次（opscore 日志按钮——前端→后端链路静态通 + curl ok:True，但浏览器点不动，根因在渲染层，只靠读代码抓不到）。
4. **台账回填与压缩复查**：X 及其关联节点入账；若漏因暴露某类 `⛔` 压缩节点/`🚧 边界外` 里藏着功能，重新评估那个压缩决策，必要时解开重测。

> 判据：一个漏检只修地图 = 学费白交；修了地图又修了方法 = 学费变成方法论。

## 两种使用模式

- **倒模模式**（测绘参考项目）：`05-insights.md` 写"可借鉴点"——它的层级怎么分、为什么好抄、映射到自己的项目该放在哪一层。**凡参考项目把某业务维度组织成了结构（层级/分组/步骤/级别/阶段），先读 `references/structure-mechanism-probe.md`**：用"是否参与寻址"判定真结构还是装饰，用四锚点抓机制，用不变量裁决哪些带走。这个判定**与我们项目是否存在无关**：项目已存在时，它用来发现被压扁的维度；项目还没建时，它决定新项目直接长出正确结构——判定结论必须写进 insights，成为设计输入。**凡功能由两个以上正交维度组合而成（源端层级 × 目标端层级、数据库类型 × 操作类型、角色 × 资源），移植前先枚举全部组合列成矩阵给用户确认，再动手实现**——组合数是设计输入不是实现细节：矩阵会直接决定 UI 形态（几栏选择框、哪些组合下固定、哪些下隐藏）。跳过矩阵直接写分支，返工次数等于组合数。真实教训：跨库同步弹窗因未先做"两级/三级 × 源/目标"矩阵表，从弹窗改视图、三栏改两栏反复推翻五轮。
- **体检模式**（测绘自己的项目）：`05-insights.md` 写"缺口清单"——`🕳️`/`🪝` 全部列出，按修补成本排序。发现"我们有标签、参考项目有结构"的落差时，读同一份 `structure-mechanism-probe.md` 做移植裁决。

两种模式都要先问一句：用户是要全量测绘还是只测某几个模块？只测部分模块时，模块边界外的节点统一标 `🚧 边界外`，不算破坏闭环，但要在概览里写明本图覆盖范围。
