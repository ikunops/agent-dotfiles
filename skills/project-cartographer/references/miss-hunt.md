# 漏检猎捕 — 漏因分类与定向补测手法

> 服务于 SKILL.md 的"漏检复盘协议"。前提认知：**系统性扫荡是注册表驱动的**——路由表、菜单工厂、命令清单、i18n、枚举这些注册表决定了你能"枚举"到什么。不在任何注册表里的功能就是隐形的，与仔细程度无关。
> 定向补测和扫荡的方法论相反：扫荡从注册表出发求全，补测从一个已知存在的功能出发求达——**先用一切手段确认它的内部名字，再顺藤摸瓜**。

## 一、八类漏因（复盘时对号入座）

| # | 漏因 | 典型症状 | 对应补测手法 |
|---|---|---|---|
| 1 | **词汇错位** | 你叫它"导出"，代码里叫 `exportData`/`extractor`/i18n 键 `grid.export…`；中英混排更甚 | 手法 A 文档先行 + B i18n 反查 |
| 2 | **无 UI 入口（headless）** | 后台任务、自动修复、一致性校验、数据迁移——地图上没有按钮指向它 | 手法 E 孤儿函数反向核查 |
| 3 | **动态注册/配置驱动** | 插件、manifest 资产、约定式发现（如 dbx 的 drivers manifest JSON） | 手法 D 配置资产扫描 |
| 4 | **过早标死胡同** | 功能藏在被压缩成 `⛔` 的"纯支撑层"或 `🚧 边界外` 里 | 复盘协议第 4 步：解开重测 |
| 5 | **跨包/跨语言边界** | 藏在 crates/packages/子模块里，前端地图标了"边界外" | 同上 + 用 01-backend 的契约面反查 |
| 6 | **非交互入口** | 快捷键、CLI 参数、深链/URL scheme、文件拖放、定时任务、外部 IPC | 手法 C 入口普查 |
| 7 | **生成物/DSL** | 功能以数据形式存在：模板、SQL 串、schema 文件、代码生成器 | 手法 D + grep 产物扩展名 |
| 8 | **复用伪装（模式的第 N 个值）** | 功能是已有功能的参数/模式值（"导出为 SQL INSERT"只是导出格式枚举的一项），扫荡看到了容器没穷举值 | 手法 F 枚举值穷举 |
| 9 | **分段拼装漏抓（抓了零件没抓总装）** | 只 grep 到 builder 定义（如菜单 6 组），实际 UI 有十几组——完整物是多个 builder 在**拼装点**按序 `flat()` 出来的，子项还作为参数传进去 | 手法 G 拼装点追查 |

## 二、七种补测手法（按命中率排序）

**A. 文档先行**：功能会先被"广告"再被实现。grep README / docs/ / CHANGELOG / `git log --oneline` 的提交信息（提交信息是现成的功能清单：`git log --oneline -50 | grep -i <概念词>`）。拿到项目自己的术语后再进代码。

**B. i18n 词表反查**：有 UI 的功能必有用户可见文案。grep i18n/locale 文件里的概念词（中英都试）→ 拿到键名 → 用键名反查组件 → 顺组件找到逻辑。**i18n 文件是事实上的功能清单**，测绘时值得单独入账一个节点。

**C. 入口普查**：交互点之外的全量入口清点——快捷键注册（`keydown`/`registerCommand`/`Shortcut`）、CLI 参数（`process.argv`/`args`）、深链（`handle(url`/`onOpenURL`）、拖放（`drop`/`onDrop`）、定时（`cron`/`setInterval`/`schedule`）、消息（`on('ipc`）。

**D. 配置资产扫描**：找 `.json`/`.yaml`/`.toml` 资产（manifest/registry/schema），它们是声明式功能清单。dbx 的 `database-drivers.manifest.json` 属于此类。

**E. 孤儿函数反向核查**：对某 API 组/服务文件列出全部导出函数 → 逐个在地图里查消费者 → 无消费者的不是死代码就是 headless 功能，二选一都要入账。这和"测完查悬空"方向相反：**悬空查 UI 有没有实现，孤儿查实现有没有被地图收录**。

**F. 枚举值穷举**：对已入账的容器（格式枚举/模式枚举/工具族），grep 完整 union 定义，逐值对照地图——地图上有容器没值的，补。

**G. 拼装点追查（定义 ≠ 全量）**：凡功能疑似"被 grep 少了"（如右键菜单只数出 6 组、截图却有十几组），**不要继续翻 builder 定义——直接找拼装点**。成熟项目里完整物是多个分段 builder 在组件内按序拼接的，子菜单/子组常作为参数传入。五步链：
1. **反查渲染点**：grep 组件模板里的菜单/列表组件标签（`<ContextMenu`/`<CustomContextMenu`），拿到 items 绑定的变量名。
2. **grep 赋值处**：搜 `变量.value =` / `setXxx(` —— 赋值右侧就是 builder 调用。
3. **grep 所有 builder 调用处**（不是定义处）：`grep -rn "createXxxMenuItems(\|buildXxxMenu("` —— 拼装点按序列出全部分组。
4. **追子菜单/子组参数**：拼装点传入的参数名（`copySubmenu:`/`filterSubmenu:`）再各 grep 一次构建处。
5. **闭环验证**：builder 数 + 子菜单数 = 截图/UI 里的组数 + 分隔线数；对不上就还有漏。

## 三、沉淀格式（复盘协议第 3 步的落盘样子）

每次有效补测，往本文件（或对应参考）追加一条：

```markdown
- **<日期> <项目>：<功能名>**（漏因 #N）
  - 触发时机：<什么场景下该想到用这手法>
  - 手法：<可执行的 grep/操作，一行>
  - 证据：<file:line>
```

阈值判断：手法是"已知手法的参数变化"（如换个 grep 词）→ 不沉淀；手法暴露了**新漏因类别或新锚点位置** → 必须沉淀。沉淀是让扫荡升级的，不是日记。

## 四、案例档案

- **2026-09 dbx（schema 层级）**：feature-matrix 早记了"缺 schema 层"缺口，但没记实现方式，缺口躺了几个迭代。→ 沉淀为 `structure-mechanism-probe.md` + "台账每项写实现指针"纪律（漏因 #1 词汇错位 + 台账粒度不足）。
- **2026-09 dbx（网格右键菜单）**：只 grep 到一个 cell builder 返回 6 组，截图却有十几组。根因：菜单是 6 个 builder 分段构建、`DataGrid.vue:12321` 按序拼装，子菜单（复制▸/筛选▸）作为参数传入。→ 沉淀为 手法 G 拼装点追查（漏因 #9 分段拼装漏抓）。
