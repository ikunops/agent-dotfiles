# 系统语义探查 —— 数据生命周期 / 权限 / 状态一致性

> 这三件事有一个共性：**都不在单个模块里，跨层才能看清**。
> 结构测绘把它们切碎到各个节点，所以永远看不全。本档案按“主题”横切。

## 一、数据生命周期

回答：数据从哪来、留多久、怎么删、出错怎么办。

### 必查六项

| 项 | 具体找什么 | 为什么重要 |
|---|---|---|
| **来源** | 用户输入 / 外部导入 / 系统生成 / 派生计算 | 决定校验策略 |
| **留存** | 软删除还是硬删除、有没有回收站、保留期多久 | 删错了能不能救 |
| **历史** | 修改是否留版本、能不能回滚、谁改的（审计） | 出事能不能追溯 |
| **导入导出** | 字段怎么映射、失败怎么处理、部分成功怎么办 | 数据能不能迁移 |
| **清理** | 有没有过期清理、清理任务在哪、失败会怎样 | 数据会不会无限膨胀 |
| **隔离** | 多租户怎么隔离（库/表/行级） | 会不会串数据 |

### 判据

- **删除语义必须明确**：看到 `DELETE` 语句要确认它是物理删还是改标记；看到 `deleted_at` 要确认查询有没有过滤它。两者都对不上 → `❓ 删除语义不明`
- **软删除的完整链路要全查**：写入标记 → 查询过滤 → 唯一约束处理（软删后同名能不能重建）→ 恢复路径。**漏一环就是 bug**
- **导入失败要有兜底**：部分成功时的事务边界、错误行怎么反馈

## 二、权限与身份

回答：谁能做什么、在哪判、判错会怎样。

### 必查五项

| 项 | 具体找什么 |
|---|---|
| **角色定义** | 角色表/枚举、角色与权限的映射 |
| **权限点** | 细粒度权限（菜单级/按钮级/数据级） |
| **校验位置** | 前端隐藏?禁用?后端拦截器?中间件? |
| **数据行级** | 只能看自己的 / 本部门的 / 全量的，怎么实现 |
| **越权响应** | 403 还是 404（404 更安全，不泄露资源存在） |

### 三个必须验证的判断

1. **前端是隐藏还是禁用？** 两者体验完全不同。禁用说明“你没权限但功能存在”，隐藏说明“你根本看不到”。**抄错这个，产品语义就变了。**
2. **后端有没有漏校验的接口？** 枚举所有路由，逐个确认有没有权限中间件。**前端隐藏 ≠ 后端安全**——直接调 API 能绕过。
3. **行级权限在哪实现？** 是在 SQL 里加 `WHERE owner_id = ?`，还是在应用层过滤？前者更安全（不会漏），后者更容易出错。

### 判据

- 前后端权限判定**必须成对核对**，只查一边不算完成
- 发现“前端隐藏但后端无校验” → 这是**真漏洞**，不是风格问题
- 权限点数量与角色数量要能对上；对不上说明有硬编码

## 三、状态归属与一致性

回答：同一份数据存了几份、以谁为准、冲突怎么办。

### 先画状态地图

找出同一份业务数据的**所有副本**：

```
数据 X 出现在：
  - 后端 DB（唯一事实源？）
  - 前端 store / 组件 state
  - URL 参数 / query string
  - localStorage / sessionStorage
  - 缓存（Redis / 内存 / CDN）
  - 其他标签页 / 其他设备
```

### 必查四项

| 项 | 问题 |
|---|---|
| **事实源** | 哪一份是权威的？代码里有没有显式声明？ |
| **同步方式** | 写操作后如何让其他副本失效？（invalidate / 推送 / 轮询 / 不处理） |
| **冲突处理** | 两处同时改，谁赢？有版本号还是后写覆盖？ |
| **刷新语义** | 页面刷新后状态还在吗？从哪恢复？ |

### 典型症状 → 根因对照

| 症状 | 大概率根因 |
|---|---|
| 保存后列表不更新 | 前端用了独立副本，写后没合并/失效 |
| 刷新前正常，刷新后丢 | 状态只在内存，没落 URL 或 storage |
| 多标签页不一致 | 没有跨标签同步机制（storage 事件 / BroadcastChannel） |
| 切换筛选后数据错乱 | 迟到的旧响应覆盖了新状态（竞态） |
| 同一个数字三处显示不同 | 多源读同一数据，未统一事实源 |

### 判据

- **必须能指出唯一事实源**。指不出 → `❓ 事实源不明`，这是隐患不是设计
- **写操作必须有明确的同步策略**：局部合并 / 精确失效 / 推送 / 轮询 / 不处理（最后一种要写清为什么可接受）
- **竞态要显式处理**：请求带序列号或 AbortController，不能靠“应该不会那么快”

## 四、三者交汇处：最容易出事的地方

| 场景 | 为什么会出事 |
|---|---|
| 软删除 + 权限 | 用户看不到自己删的数据，但有权限的管理员能看到 → 数据隔离要按角色分别设计 |
| 多租户 + 缓存 | 缓存键没带租户 ID → 串数据 |
| 导入 + 状态副本 | 批量导入后前端列表没刷新 → 用户以为失败又导一遍 |
| 权限 + 乐观更新 | 前端先乐观显示成功，后端 403 → 界面显示成功但实际没有 |

**这三件事要一起看，不能分开查。**

## 五、产物格式

```markdown
## 系统语义档案：<模块名>

### 数据生命周期
- 来源：用户输入 `file:line`
- 删除：软删除，`deleted_at` 在 `file:line`；查询过滤在 `file:line` ✓
- 唯一约束：软删后同名可重建（部分索引）`file:line`
- 未覆盖：导入失败的事务边界 `❓`

### 权限
- 角色：admin / editor / viewer `file:line`
- 前端：无权限菜单**隐藏**（不是禁用）`file:line`
- 后端：所有路由过 `requirePerm` 中间件 ✓；例外：`GET /api/public` 故意开放 `file:line`
- 行级：SQL 里加 owner_id 过滤 `file:line`

### 状态
- 事实源：后端 DB
- 副本：前端 store（无持久化）、URL query
- 写后同步：invalidate query + 局部合并 `file:line`
- 跨标签：无处理 `⚠️ 已知限制`
```

## 六、判据

- **三者必须成对核对**：数据+权限、权限+状态、状态+数据。单独看每一项都会漏
- **发现的问题要分性质**：`🔒 安全` / `💾 数据风险` / `🔄 一致性`，不同性质修复优先级不同
- **没有显式声明的事实源 = 隐患**，不能默认“应该是对的”
