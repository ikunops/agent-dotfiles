# 实现档案 —— 把“有什么”变成“怎么做”

> 结构测绘回答“在哪、通不通”，本档案回答“**它内部是怎么实现的**”。
> 适用时机：某个功能值得倒模、值得借鉴、或值得体检时。全量测绘不需要对每个节点都做。

## 一、什么时候做

命中任一即做：

- 准备倒模这个功能（要照着写一遍）
- 这个功能的实现方式明显比同类巧妙（值得学习）
- 体检时怀疑这里有隐患（要看清机制）
- 用户明确问“它是怎么做的”

**不做**：纯 CRUD、框架脚手架生成的样板代码、一行委托。

## 二、四个必查维度

### 1. 业务规则

提取这个功能“什么算对、什么算错”的判定逻辑，而不是它的代码样式。

| 要提取 | 具体找什么 |
|---|---|
| 校验条件 | 字段级校验、跨字段校验、业务前置条件 |
| 状态机 | 有哪些状态、允许哪些迁移、非法迁移怎么处理 |
| 不变量 | 任何时候都必须成立的条件（余额不为负、订单总额=明细之和） |
| 边界处理 | 空值、零值、极值、并发冲突、重复提交 |
| 权限判定 | 谁能做什么、判定发生在哪一层 |

**输出格式**：规则清单 + 每条规则的 file:line。规则必须能被验证（写得出反例），写不出反例的说明还没理解。

### 2. 数据模型

| 要提取 | 具体找什么 |
|---|---|
| 表/结构设计 | 字段、类型、可空性、默认值 |
| 关系 | 一对多/多对多的实现方式（外键/关联表/嵌套文档） |
| 索引 | 建在哪些字段上、为什么（对应哪条查询） |
| 约束 | 唯一约束、检查约束、级联删除策略 |
| 软删除 | 是否软删、删除标记字段、查询时是否过滤 |
| 审计 | 谁改的、什么时候改的、是否留历史 |

**关键**：索引和查询要**成对提取**——只记索引不记它服务的查询，等于没记。

### 3. 技术选型与取舍

这一维最容易漏，但倒模时最值钱。要提取的是**为什么这么选**，不是选了什么。

| 信号 | 说明 |
|---|---|
| 代码注释里的“因为…所以…” | 作者的显式说明 |
| 依赖清单里的非常规依赖 | 为什么要引入它 |
| 同一问题有两种实现 | 说明做过取舍，找废弃的那份 |
| 配置项 | 暴露给运维的开关 = 作者认为会变的东西 |
| 版本兼容层 | 说明有过迁移，找旧方案 |

**输出要求**：如果找不到显式说明，只能写“实现方式为 X，替代方案未知”——**不许编造理由**。

### 4. 关键路径

| 要提取 | 具体找什么 |
|---|---|
| 事务边界 | 哪些操作在一个事务里、失败怎么回滚 |
| 并发控制 | 锁、乐观版本号、唯一约束兜底 |
| 缓存 | 缓存什么、TTL、失效策略、穿透保护 |
| 失败重试 | 有没有重试、退避策略、幂等性保证 |
| 异步 | 队列/事件/定时任务，以及失败后的兜底 |

## 三、产物格式

```markdown
## 实现档案：<功能名>

### 业务规则
- 规则 1：<可验证的描述>  `file:line`
- 规则 2：...

### 数据模型
- 表 `<name>`：字段 a/b/c；索引在 (x,y)，服务查询 `<query>`  `file:line`
- 软删除：是/否；查询过滤在 `file:line`

### 选型与取舍
- 用了 <方案>；代码注释说明“因为…”，`file:line`
- 未找到替代方案说明 → 标 `❓ 取舍未知`

### 关键路径
- 事务：`BeginTx` 在 `file:line`，覆盖 A/B/C 三个写操作
- 并发：乐观锁 version 字段，`file:line`
- 缓存：TTL 60s，失效在写后 `file:line`

### 复刻时必须一起带走的东西
1. <离开它就复刻不出同样行为的机制>
2. ...
```

## 四、判据

- **每条结论都要有 file:line**；没有的标 `❓ 推测`
- **规则必须可验证**：能写出一个违反它的输入
- **取舍不许编**：找不到说明就写“未知”，不要替作者合理化
- **最后一节最重要**：把“不可省略的机制”单独列出来，这是倒模的检查表
