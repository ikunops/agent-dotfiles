# 品质档案 —— 它为什么好用、为什么好看、为什么快

> 结构闭环只证明“能跑通”，不证明“跑得好”。本档案专门提取**涌现品质**：视觉、流畅、性能。
> **硬判据：没有运行证据的品质结论，一律标 `⚠️ 未验证`，不许写成事实。**

## 一、为什么必须运行

结构是**声明**（路由表、组件树、字段定义），读代码就能得到。
品质是**涌现**（几十个微决策的累积），读代码只能看到结果，看不到约束和取舍。

举例：代码写 `transition: 150ms ease-out`，读到的是参数；
但“这个交互感觉干脆”来自 150ms + 缓动曲线 + 触发时机的共同作用——只有真操作才知道。

## 二、视觉维度

目标：把“好看”拆成可量测的量，而不是形容词。

| 量测项 | 怎么测 | 输出 |
|---|---|---|
| 间距序列 | 截图后量元素边缘间距，收集全部值 | 实际使用的档位（如 4/8/16/24） |
| 字阶 | 量标题/正文/辅助的字号 | 实际比例（如 1.25） |
| 色板 | 采样主色/语义色 | 色值 + 用途 |
| 圆角 | 量各层级圆角 | 是否同心（外=内+间距） |
| 动效时长 | 录屏或 DevTools 测 | 各交互的实际 ms |
| 缓动曲线 | 从 CSS 读 cubic-bezier | 每种意图用的曲线 |
| 对比度 | 计算前景/背景亮度比 | 是否达 4.5:1 |

**必须截图**：不能只读 CSS。CSS 里写了 `border-radius: 16px`，但实际渲染可能被父容器或 `overflow` 影响。

**输出格式**：量测值 + 截图 + “这套参数为什么协调”的一句话判断。判断要基于量测，不是感觉。

## 三、流畅维度

目标：把“顺手”拆成时序和状态。

必须真操作，记录每一步的时间和状态：

| 测什么 | 怎么测 | 好的标准 |
|---|---|---|
| 反馈延迟 | 点击到 loading 出现的耗时 | < 100ms（超过就感觉卡） |
| 完成反馈 | 操作完成到提示出现的耗时 | 有明确成功/失败信号 |
| 失败恢复 | 制造失败，看提示与重试路径 | 用户输入不丢、错误可读、有重试 |
| 重复提交 | 连续快速点击 | 有防重或幂等，不会产生两条 |
| 中断恢复 | 操作中途关页面/切路由 | 状态不脏，回来能继续 |
| 空/加载/错误态 | 逐一构造 | 三态都有明确画面，不白屏 |

**记录格式**：`操作 → t+0ms 点击 → t+80ms loading 出现 → t+600ms 结果显示`

## 四、性能维度

目标：找到作者的**规模假设**——这是倒模时最该带走的东西。

| 找什么 | 在哪找 | 说明什么 |
|---|---|---|
| 分页大小 | API 参数、`LIMIT`、常量 | 作者认为单页合理量 |
| 虚拟滚动阈值 | 列表组件的启用条件 | 作者认为多少条以上需要虚拟化 |
| 索引 | 建表语句 / migration | 作者认为哪些查询是高频的 |
| 缓存 TTL | 缓存配置 | 作者认为数据多久会变 |
| 并发上限 | 连接池、worker 数 | 作者预期的负载 |
| 懒加载边界 | 路由分包、图片 loading | 作者认为什么可以先不加载 |

**更关键的是实测**：

- 首屏加载时间（Network 面板）
- 大数据量下的响应时间（构造 100/1000/10000 条测）
- 内存占用（DevTools Memory）

**如果测不了**（没有测试数据、环境不允许），写“规模假设为 X（来自代码），实测未做 `⚠️`”，不许编造性能结论。

## 五、产物格式

```markdown
## 品质档案：<功能名>

### 视觉（附截图）
- 间距序列：4 / 8 / 16 / 24（量测自 <位置>）
- 字阶：32 / 20 / 15 / 14 / 12 → 比例约 1.3
- 圆角：卡片 16，内部按钮 8，外=内+8 → 同心 ✓
- 动效：进入 240ms cubic-bezier(0,0,0.2,1)
- 判断：<为什么这套参数协调，基于以上量测>

### 流畅（附操作记录）
- 点击 → 80ms loading → 600ms 结果
- 失败路径：错误提示 2s 后出现，输入保留 ✓
- 重复提交：按钮点击后立即 disabled ✓

### 性能（附实测或标 ⚠️）
- 分页 20 条（`file:line`）
- 列表 > 200 条启用虚拟滚动（`file:line`）
- 实测 1000 条响应 180ms

### 复刻时必须保持一致
1. <离开它品质就掉的参数>
2. ...
```

## 六、判据

- **没有运行证据 → 一律 `⚠️ 未验证`**，不许写成“它的动效很流畅”
- **量测值优先于形容词**：写“240ms cubic-bezier(0.4,0,0.2,1)”而不是“很顺滑”
- **性能结论必须带规模前提**：“1000 条下 180ms”比“性能不错”有用一万倍
- **性能测不了就明说**，不许拿代码里的分页大小冒充实测结果
