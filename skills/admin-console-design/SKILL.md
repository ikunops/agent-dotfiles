# 后台 / 控制台设计规范

面向**信息密度高、以数据为主角**的产品：后台、管理台、监控面板、运维平台。

核心立场：**这类产品的"好看"不是装饰出来的，是约束出来的。**
三档约束同时生效——画布硬规则保正确，视觉令牌保手感，产品结构法则保方向。

## 一、三档约束模型（先理解这个，再看数字）

| 层 | 管什么 | 举例 |
|---|---|---|
| **画布硬规则** | 能不能画对 | flex 优先；卡片高度必须 hug（不被拉伸）；表格必须 `frame → row → cell → content` 四层；图标必须是 SVG 组件，不能拿符号字充数；颜色只能走变量 |
| **视觉令牌准则** | 好不好看 | 间距节奏、字阶、圆角层级、卡面处理；禁止"AI 味"排版（居中大标题 + 三等分卡片） |
| **产品结构法则** | 对不对 | 一屏只回答一个问题；只有一个主视觉区；只有一个主操作；状态必须可见；密度一致 |

**失效顺序**：结构错了，令牌救不回来；令牌乱了，硬规则也撑不住。
所以**检查时**按"结构 → 令牌 → 硬规则"，**执行时**反过来（先立硬规则，再铺令牌，最后定结构）。

> 这套模型的**通用表述**（不限于后台）在 `opendesign` skill 里；本节是它在后台类产品上的具体化。

## 二、执行工作流（拿到任务先走这 6 步）

| 步 | 动作 | 输入 | 产出（必须落盘/可见） |
|---|---|---|---|
| 1 | **定义每屏的问题** | 用户 brief、现有路由/导航、真实业务对象 | 页面清单：每页一行「页面 → 只回答的那个问题」 |
| 2 | **定主视觉与主操作** | 页面清单、真实数据字段 | 每页一个主视觉区 + 一个主操作；其余降为配角 |
| 3 | **立骨架与令牌** | 项目类型、主题数量、技术栈 | 侧栏/顶栏/内容区骨架；引用 `references/console-tokens.css` 或项目现有 token |
| 4 | **列状态与写后同步矩阵** | 每个页面涉及的数据、权限与写操作 | 空 / 加载 / 错误 / 权限受限四态；每个写操作标明「局部更新 / invalidate / 实时 / 轮询」策略，缺哪项就补哪项 |
| 5 | **做页面与外壳** | 步骤 1–4 的产物 | 页面正文 + 声明式外壳；页面之间只改正文，不复制侧栏/顶栏 |
| 6 | **按顺序验收** | 页面成品 + 页面清单 | 结构 → 令牌 → 硬规则三层检查；验收交给 `ui-acceptance` |

**执行顺序固定：结构 → 令牌 → 硬规则。** 先确认“这屏该回答什么”，再选数字和组件；反过来会得到“很整齐但答非所问”的面板。

**最小交付物**（新建后台时缺一不可）：

1. `页面清单`：页面名 + 每页唯一问题 + 主视觉 + 主操作
2. `状态与写后同步矩阵`：每页的空/加载/错误/权限四态 + 每个写操作的同步策略（详见 `debug-and-refactor` Part E15）
3. 一套主题变量：直接引用 `references/console-tokens.css`，或在项目 token 中定义同名变量
4. 页面骨架：侧栏 240 + 顶栏 64 + 弹性主区（`min-width: 0`）
5. 验收记录：结构/令牌/硬规则各一项通过证据

### 先判断任务形态

| 任务 | 走法 |
|---|---|
| 从零做后台/监控面板 | 完整走 6 步；第 1 步没有页面清单不进入第 2 步 |
| 给已有后台统一视觉 | 先盘点现有页面与 token；只走第 3、6 步，不重画信息架构 |
| 只做一个页面/组件 | 走第 1、2、4、6 步；复用现有外壳与 token，不新建一套 |
| 在 Ardot 画布上作业 | 骨架与布局遵守 Ardot 8 点网格；其余步骤相同；不要混用本 skill 的 12/20 间距 |

**开工第一句必须报出**：任务形态（从零/统一视觉/单页/Ardot）+ 第 1 步产出的页面问题清单。没有这句话，视为还没完成第 1 步。

### 失败分支（遇到就别硬画）

| 触发条件 | 一线处理 | 仍失败时 |
|---|---|---|
| 用户没给业务对象、页面范围或真实数据 | 先列“已知 / 缺失”清单，只问会改变页面结构的问题；最多 3 个 | 用明确标注的占位数据出低保真骨架，禁止把假数据当真实业务 |
| 没有现成设计系统或 token | 先查项目 `./opendesign/design-systems/` 与全局 `$DOTFILES/design-systems/`；找到就复用 | 没有就明确采用本 skill 默认令牌；不要临时发明第二套变量 |
| 主题色/品牌色缺失 | 用 `references/console-tokens.css` 四套主题里最接近的一套，并写出选择理由 | 品牌方向必须用户拍板；在拍板前只做结构和灰度稿 |
| 状态数据拿不到（空/错误/权限） | 按状态矩阵先画静态态，标“待接真实数据” | 不把加载态伪装成空态；无法验证的状态在验收记录里标 `未验` |
| Ardot 插件/画布不可用 | 明确告知不可用，退回 HTML/静态稿，间距改用本 skill 四档 | 不伪造 Ardot 产物，不声称已在画布上验证 |
| 页面超过 9 个或导航层级超过 3 层 | 先停在信息架构阶段，输出分组与下钻关系让用户确认 | 未确认前不批量生成页面，避免把错误结构复制 9 次 |
| 现有页面与规范冲突 | 先列冲突项（尺寸/间距/主题/结构），区分“历史债”与“本次范围” | 不借统一视觉之名重画信息架构；范围外冲突只登记不擅自改 |

**🔴 CHECKPOINT · 设计系统与范围确认**：任务形态、页面清单、采用的设计系统（或默认令牌）三项没有同时说清，**不准进入画布/代码实现**。

**🔴 CHECKPOINT · 结构定稿**：页面唯一问题、主视觉、主操作、四态矩阵未定稿，**不准开始铺视觉细节**。

**🔴 CHECKPOINT · 交付前**：结构 → 令牌 → 硬规则三层验收没有证据，**不准说“完成”**。

## 三、令牌表

### 字阶 —— 五档，不许多一档

| 角色 | 字号/字重 | 行高 | 用途 |
|---|---|---|---|
| KPI 数值 | 30 / 700 | 1.2 | 指标卡主数字 |
| 页面标题 | 20 / 700 | 1.3 | 每屏一个 |
| 卡片标题 | 15 / 600 | 1.35 | 区块标题 |
| 正文 | 14 / 400 | 1.6–1.7 | 默认文本 |
| 辅助 | 12–13 / 400 | 1.5 | 时间戳、单位、次要说明 |

规则：**只允许这五档。** 想要"看起来更重"时改字重或颜色，不要加第 6 档。
同样 14px，卡片里的元信息用更松的行高——"松紧对比"来自行高，不来自字号。

### 间距 —— 24 / 20 / 16 / 12，四档循环

| 位置 | 值 |
|---|---|
| 内容区 padding | 24 |
| 区块之间 gap | 20 |
| 卡片 padding | 20 |
| 卡片内部元素 gap | 12–16 |
| 列表行内 padding | 12–14 |
| 图标与文字 gap | 8–12 |

规则：**全程只用这四个数**，不出现 18、22 这类中间值。"整齐"的本质是节奏收敛，不是间距小。

### 尺寸 —— 固定骨架 + 弹性主区

| 元素 | 值 |
|---|---|
| 侧边栏 | 240（`flex: 0 0 240px`） |
| 顶栏 | 64 |
| 右侧信息卡 | 380 |
| 详情卡 | 460 |
| 按钮高 | 40（小号 34 / 38） |
| 输入框 | 44 |

规则：**主区永远拿 `1fr`，固定卡永远给死宽度**，这样图表卡是主角、右侧是配角，主次不会打架。
⚠️ 弹性区必须配 `min-width: 0` —— flex 子项默认 `min-width: auto`，超长内容会把容器撑破。

### 层级 —— 靠"反转"做纵深，不靠阴影

```
画布 bg-canvas  →  卡片 bg-surface（浮起）  →  卡片内的行回落成 bg-canvas  →  语义色只表态（成功/警告/危险）
```

为什么不用阴影：**阴影只在浅色主题有效，深色下基本失效。**
用"描边 + 背景反转"两套主题都稳。唯一例外是真正的浮层（下拉、弹窗、登录卡），它们本来就在"上面"。

### 圆角 —— 三档

`6`（小控件、chip）/ `8`（按钮、输入框）/ `14`（卡片）。
嵌套时外层圆角 ≥ 内层，避免"内圆角比外圆角还大"。

## 四、多主题架构（一套令牌，N 套配色）

原则：**组件样式里不出现任何字面颜色，只引用语义变量。** 换肤 = 换变量集。

```css
:root, [data-theme="dark"] { --bg-canvas:#0b0f17; --bg-surface:#131a25; --brand:#3d8bff; }
[data-theme="light"] { --bg-canvas:#f5f7fa; --bg-surface:#ffffff; --brand:#2563eb; }
```

- 语义变量分三层：**背景**（canvas / surface / elevated）、**文字**（primary / secondary / muted / inverse）、**语义色**（brand / accent / success / warning / danger）+ 图表色（chart-a..d）
- 每个主题都要给**全套**变量，不能只覆盖差异项——漏一个就串色
- 切换写 `data-theme` 到 `<html>` 并存 localStorage
- **局部 `data-theme` 做同屏对比**：设计系统页里四张卡各自锁定一套主题，用户直接对比，不用来回切
- 深色下"卡片内回落成 canvas 色"的行，在浅色下同样成立——反转关系是结构性的，不依赖具体色值

可直接用的令牌文件见 `references/console-tokens.css`（4 套主题 + 尺度令牌）。

### 语义色用法（血泪教训：别无脑白字）

原稿的做法是"实色底 + 白字"做徽标 —— 实测**四套主题里有 4 处不达标**：

| 组合 | 实测对比度 | 问题 |
|---|---|---|
| 白字 / 深色主题 brand `#3d8bff` | 3.31 | 亮蓝压白字不够 |
| 白字 / vibrant brand `#ff6a3d` | 2.85 | 亮橙更糟 |
| 白字 / dark success `#2ed47a` | 1.94 | 亮绿几乎看不清 |
| 白字 / vibrant success `#12b76a` | 2.62 | 同上 |

**正确做法**：每个语义色给三个变体，按底色深浅选前景：

```css
/* 浅底 + 深字（推荐做徽标，密度高也不刺眼） */
.badge { background: var(--success-soft); color: var(--success-ink); }
/* 实心底 + 白字（仅在 solid 已压暗到 >=4.5 时可用） */
.badge-solid { background: var(--success-solid); color: #fff; }
/* 实心主按钮：前景用 --on-brand，不要写死 #fff */
.btn-primary { background: var(--brand); color: var(--on-brand); }
/* 品牌色当"文字"用时（链接、强调数字）必须换 --brand-ink */
.link { color: var(--brand-ink); }
```

`--on-brand` 是每套主题算好的：深色主题和 vibrant 用**深字**，浅色和 mono 用**白字**。

**规则**：任何"色底 + 字"的组合都必须实测 ≥4.5:1，不许凭感觉选白色。

### 求解对比度时最容易踩的两个坑（都是实测踩出来的）

**坑一：拿脚本"卡着 4.5 线"解出来的 `-ink` 会变成灰色。**
固定浅底、只调明度去逼近 4.5，最快命中的解往往饱和度极低——`#90a19e`、`#676f6a` 这类"绿不绿灰不灰"的值，检测能过，但徽标看起来是脏的。
正确解法是**保留色相与饱和度、只压明度**（HLS 里锁 H/S 调 L），得到 `#4ade80` / `#166534` 这种"还是绿的绿"。**过检测不等于好看。**

**坑二：`text-muted` 常常被漏检，但它也是真实文本。**
深色底上的辅助灰最容易掉到 4.0 以下。要求是**在三层背景（canvas / surface / elevated）上都 ≥4.5**，按最暗的那层（elevated）取值——例如深色主题 `#8b95a5`。

## 五、声明式外壳复用（多页面站点的省力法）

9 个页面重复写侧边栏/顶栏 = 9 处维护。改用属性声明 + 一处渲染：

```html
<aside class="sidebar" data-menu="monitor" data-active="hosts"></aside>
<header class="topbar" data-title="资源管理" data-chip="生产环境"></header>
```

JS 读属性渲染外壳，页面正文保持真实语义化 HTML。
好处：改导航只改一处；新增页面零复制。
图标用内联 SVG + `stroke="currentColor"`，自动跟随主题与文字色（配合 `no-emoji-ui`）。

## 六、产品结构法则（这一档最容易忽略）

1. **一屏只回答一个问题** —— 首页答"现在健康吗"，列表页答"有哪些资源"，详情页答"这台机器怎么样"
2. **只有一个主视觉区** —— 弹性区给最重要的那张图/表，其余降为固定宽度配角
3. **只有一个主操作** —— 顶栏右侧永远只有一个主按钮，其余降为次要（不出现"三个蓝按钮抢焦点"）
4. **状态必须可见** —— 空 / 加载 / 错误 / 权限受限，四种都要有画面，不是只做"有数据"的理想态
5. **密度一致** —— 同类页面的信息密度要接近，不能列表页很密、详情页很空

## 七、反例黑名单（不要这么做）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| 1 | 先画侧栏、卡片和主题，再想这屏回答什么 | 页面会“很整齐但答非所问”，返工要重画结构 | 先写页面唯一问题，再定主视觉与主操作 |
| 2 | 每张卡片都做成大主视觉 | 每块都抢焦点 = 没有主次 | 只留一个弹性主区，其余用固定宽度配角 |
| 3 | 居中大标题 + 三等分卡片 | 最典型的“AI 味”排版，信息之间没有真实层级 | 用主视觉区 + 固定配角区，按业务关系排布 |
| 4 | 顶栏同时放三个主按钮 | 动作层级消失，用户不知道下一步点哪个 | 一个主操作；其余降为次按钮或菜单 |
| 5 | 只画“有数据”的理想态，或只做写入不设计写后同步 | 空/加载/错误/权限和“保存后看不到新数据”都会在上线后才暴露 | 先过状态矩阵与写后同步矩阵：四态都有画面，每个写操作有明确的局部更新/失效/推送策略（`debug-and-refactor` Part E15） |
| 6 | 统一视觉时顺手重画导航和信息架构 | 超出用户授权范围，改动面不可控 | 只统一 token/骨架；结构变更另开任务 |
| 7 | 为每页复制一份侧栏/顶栏 | 9 个页面 9 处维护，必然漂移 | 声明式外壳 + 一处渲染 |
| 8 | 组件里写死颜色、字号、间距、阴影、z-index | 换肤必然串色，跨页面必然不一致 | 只引用语义变量和尺度 token |
| 9 | 加第 6 档字号或 18/22 这类中间间距 | 破坏五档字阶和四档间距，节奏立刻散 | 用字重/颜色强调；间距只用 24/20/16/12 |
| 10 | 弹性区不写 `min-width: 0` | 长内容会把主区撑破，表格和图表溢出 | 弹性子项加 `min-width: 0`，固定卡给死宽度 |
| 11 | 用符号字或 emoji 当生产 UI 图标 | 跨平台字形不一致，无法随主题和状态变化 | 用内联 SVG + `currentColor`，配合 `no-emoji-ui` |
| 12 | 深色主题堆阴影做层级 | 深色下阴影基本失效，层级看起来发灰 | 用背景反转 + 描边做纵深 |
| 13 | 在 Ardot 画布混用 12/20 间距 | 与 8 点网格错位，出现“处处差 4px” | 画布用 4/8/16/24/32/48/64；代码用本 skill 四档 |
| 14 | 色底 + 白字凭感觉选，或拿灰调解当作 `-ink` | 对比度经常不到 4.5:1，徽标会发脏 | 每个主题实测；保留色相/饱和度压明度；徽标优先 soft 底 + ink 字 |
| 15 | 没跑三层验收就说完成 | 观感不是证据，交付不可复现 | 结构 → 令牌 → 硬规则逐层给证据 |

## 八、规范管不了什么（诚实边界）

**规范保的是下限**：保证对齐、节奏、层级不出错。它管不了真实数据的极端情况——

- 超长主机名 / 超长文本怎么截断（`text-overflow: ellipsis` + `title` 提示，还是中段省略）
- 0 条数据的空态长什么样
- 1000 行表格的虚拟滚动 / 分页策略
- 权限受限时的降级态

这四样必须在"有数据"的理想态之外单独设计，否则上线即翻车。

## 九、出处与一个必须知道的冲突（2026-10-17 查证）

这套模型不是凭空的。逐条对照 Ardot 官方规范后，**结论是分层的**：

| 层 | 来源 | 证据 |
|---|---|---|
| **产品结构法则**（5 条） | **Ardot 官方** | `ardot-ui-design/references/guidelines-web-app.md` 的 16 条「universal product design principles」：§1 Purpose First / §2 Dominant Region / §6 Status Visibility / §7 Action Hierarchy / §9 Density Intentionality —— 5 条**逐条对应** |
| **画布硬规则** | **Ardot 官方** | `ardot-design-core/rules/design-rules.md`：flexbox 优先、`hug_contents` 卡片、SVG 图标必须是独立 frame+svg 节点、颜色走 variables、禁 emoji/符号字 —— 均**原文可查** |
| **视觉令牌的具体数字** | **会话自定**（个别数字在官方示例里出现过，但都不是标准） | 字阶 `30/20/15/14/12`、间距 `24/20/16/12` 官方**查无**；`240` 只出现在 `batch-edit.md` 的侧栏**示例代码**里，`380` 只出现在 style-guide 提取模板的卡片**示例**里 —— 是举例，不是声明标准 |

⚠️ **一个真冲突：间距档不一样。**

- **Ardot 官方** spacing scale：`4, 8, 16, 24, 32, 48, 64`（8 点网格）
- **本 skill**：`24 / 20 / 16 / 12`

`20` 和 `12` **不在** Ardot 的档位里。所以：

> **在 Ardot 画布上作业时，跟随 Ardot 的 8 点网格（4/8/16/24/32/48/64）；写代码/静态站点时，用本 skill 的四档。**
> 两者不要混着用——混用正是"看起来齐、但处处差 4px"的根源。

另外：Ardot 的**字阶不是固定的**，它靠 `search_style_guide` + `build_style_guide` 动态生成。所以本 skill 那 5 档是"没有风格库时的默认值"，不是硬标准。

**用词提醒**：`ardot-ui-design` / `ardot-design-core` 等 6 个 skill 是 **WorkBuddy 内置插件**（`workbuddy-builtin/ardot`），不在本仓库里，也不该复制进来——它们随插件升级。本 skill 只吸收其**结论**，不搬运其文本。

## 与其它 skill 的分工

- `opendesign` = **通用入口**（任何设计任务）：三档约束模型的**通用表述** + 产品界面数字预设 + anti-slop；本 skill 是它的"后台类"展开版

- 本 skill = **正向标准**（该做成什么样，给数字）
- `frontend-ui-consistency` = **相对一致性审计**（项目内 A 页 vs B 页是否一致，刻意不设绝对标准）
- `ui-acceptance` = **交付验收**（四层验收 + 硬阈值）
- `html-dashboard-regression` = **验证方法**（jsdom 跑逻辑 + 无头浏览器量布局）
- `workbench-layout` = **布局陷阱**（z-index 预算、滚动隔离、右键菜单溢出）
- `dashboard-builder` = **监控平台的指标选型**（该放哪些面板，不是怎么画）
- `create-design-system` / `opendesign` = **品牌向设计系统**（从既有品牌提取，输出 tokens + UI kit）
