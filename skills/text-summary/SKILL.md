# Text Summary

把长文本压成能直接用的三段式摘要。默认不提问、不问背景，拿到文本就出结果。

## 触发条件

命中任一即用本 Skill：

| 触发信号 | 示例 |
|---|---|
| 显式求摘要 | "总结一下"、"给我个摘要"、"提炼要点"、"summarize"、"TL;DR" |
| 抱怨长度 | "太长不看"、"这么长谁看得完"、"有没有短版" |
| 求内容 | "这段讲了什么"、"重点是什么"、"结论是啥" |
| 求汇总 | "汇总成要点"、"整理一下"、"recap 一下" |

不适用：逐字精校、翻译、全文改写、要求保留原文措辞。

## 输入

| 参数 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `text` | 是 | — | 待摘要原文。可粘贴、可给文件路径、可给 URL |
| `mode` | 否 | `standard` | `brief` ≤5% 长度 · `standard` ≤15% · `detail` ≤30% |
| `audience` | 否 | 通用 | 指定读者会改变术语密度（如"给老板看"、"给新人看"） |
| `lang` | 否 | 跟随原文 | 输出语言 |

缺失处理：`text` 为空 → 直接回"没有可摘要的内容，请贴入原文或给出文件路径"，不追问其他参数。

## 步骤

1. **定规模与模式** — 统计原文字符数。未给 `mode` 时按长度定：<300 字 → `brief`；300–8000 字 → `standard`；>8000 字 → `standard` + 分段处理。
2. **分段** — 原文 >8000 字时，按原有空行/标题切成若干块，逐块做步骤 3–5，最后合并去重。≤8000 字不分段。
3. **抽事实** — 通读一遍，只标出可验证项：数字、日期、专有名词、决策、结论、动作项。跳过修饰语、重复表述、寒暄。
4. **写核心结论** — 1–3 句，回答"这段东西最终要说明什么"。禁止"本文主要介绍了…"式空壳开头。
5. **列关键要点** — 3–7 条，每条 ≤40 字，主语明确，必须带上原文里的数字或专有名词。
6. **提待办与风险** — Action 写成"谁 / 做什么 / 何时"；Risk 写不确定、缺失、冲突项。没有就写"无"，不硬凑。
7. **自检回原文** — 逐条核对：每条要点在原文有依据、数字与原文一致、无原文外的新增信息。核对不通过的条目直接删除，不保留可疑内容。

### 失败分支

| 情况 | 处理 |
|---|---|
| 原文乱码、截断、中途断句 | 先声明"输入不完整：第 X 段后缺失"，只对可读部分做摘要，末尾标注未覆盖范围 |
| 原文无实质信息（纯客套、纯重复） | 输出"原文无可摘要的实质信息"＋原因说明，不编造要点 |
| 原文事实自相矛盾 | 并列写出矛盾双方，各自标 `[冲突]`，不做单方面取舍 |
| 要点凑不满 3 条 | 有几条写几条，不注水、不重复拆分同一事实 |

## 输出

严格按此模板，不做额外寒暄：

```markdown
## 摘要 · <来源标题，无标题则写"未命名">
- 原文规模：<N> 字 · 模式：<mode> · 长度占比：<x%>

### 核心结论
<1–3 句>

### 关键要点
1. <≤40 字，含数字或专有名词>
2. …

### 待办与风险
- Action：<谁 / 做什么 / 何时>。无则写"无"
- Risk：<不确定、缺失、冲突>。无则写"无"

> 覆盖度：<已处理段数>/<总段数>｜未覆盖：<范围或"无">
```

## 硬约束

- 不新增原文没有的信息，不做推断式补充
- 数字、单位、专有名词逐字保留，不换算、不约数
- 禁用"综上所述""值得注意的是""总而言之""不难看出"
- 总长不超对应 `mode` 的长度上限；超了就砍要点，不砍核心结论

## 调用示例

**输入**

```
text: |
  本周 NodeDeck 桥接服务（:8801）连续三次在凌晨 2 点断连，日志显示 upstream
  timeout 超过 30s。排查发现是 OpsCore agent 端口 8089 的心跳间隔从 10s 被改成
  60s，桥接侧 read deadline 仍是 15s，于是每次都被判死。KM1（192.168.94.20）
  受影响最严重，KN1/KN2 只出现一次。周三把心跳改回 10s 后未再复现。遗留问题：
  桥接服务没有重连退避，网络抖动一次就永久断开，需要补 retry。
mode: standard
audience: 给老板看
```

**输出**

```markdown
## 摘要 · 未命名
- 原文规模：214 字 · 模式：standard · 长度占比：14%

### 核心结论
NodeDeck 桥接服务凌晨断连的根因是 agent 心跳间隔被改长（10s→60s）后超过桥接侧
15s 读超时，改回 10s 后故障消失；重连退避缺失仍是未修复的隐患。

### 关键要点
1. 桥接服务 :8801 一周内凌晨 2 点断连 3 次，日志报 upstream timeout >30s
2. 根因：agent :8089 心跳 10s 改 60s，桥接 read deadline 仍 15s，心跳被判死
3. KM1（192.168.94.20）受影响最重，KN1/KN2 各仅 1 次
4. 周三心跳改回 10s 后未再复现
5. 遗留：桥接无重连退避，一次抖动即永久断开

### 待办与风险
- Action：开发补桥接服务重连退避（retry backoff），无明确负责人与 deadline
- Risk：原文未说明心跳为何被改成 60s，存在被再次改回的风险

> 覆盖度：1/1｜未覆盖：无
```

更多可运行示例见 `examples/`。
