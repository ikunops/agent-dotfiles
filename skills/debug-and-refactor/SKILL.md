# 排障与复用方法论（Debug & Refactor）

从若干次真实排查（按钮"× 删不掉"反复修不好；多个同结构行/按钮重复；"改过没生效"是跑旧构建；多主机操作作用到错误对象）中提炼的通用思维习惯。适用于任何语言 / 项目，不绑定具体技术栈。

## 核心原则

- **先核查前提，再定位，再动手修。** 很多"假 bug"是源码/部署物/环境/数据/目标假设错了，代码本身没毛病。
- **「不存在」这类否定结论，必须写明搜索范围与命令。**只在一个平面里找就断言"不存在"，是最容易骗过自己的假阴性。2026-09-18 一天内三次同类：`git` 用本地（**陈旧**）ref 判断谁新 → 应问 `git ls-remote` / `push --dry-run`；`fsck` **只查 ref 可达对象** → 应再覆盖远端最新提交；`ls skills`（只看顶层）判断 skill 不存在 → 应递归 `find skills -iname "*<名>*" -name SKILL.md`。
- **症状类 bug（点了没反应）：先定位"层"，再动手修。** 不要一上来就改样式。
- **抽象与修通同等重要。** 代码出现第 2 份重复时就要停下来评估复用，而不是照抄第三次。

排障顺序建议：**Part D 前提核查（30s 快筛）→ Part A 层级二分 → Part C 完整闭环 → Part B 复用**。

## Part A —— 症状类 bug 排障法

当用户说"某按钮/操作点了没反应 / 删不掉 / 不生效 / 没变化"时：

1. **先二分「事件层 vs 样式层」**
   - 事件层：`onClick`/监听没触发，或回调逻辑出错。
   - 样式层：事件其实触发了、逻辑也生效，但视觉上被遮挡 / 覆盖 / 布局溢出，让人以为"没反应"。
   - 判断手段：该按钮/元素是否被另一个元素盖住？同一个逻辑在其他入口是否生效？看 DOM 结构与事件绑定，而不是只看 CSS。

2. **用「最小对比」定位**
   - 找一个"能正常工作"的同类对照（例如另一个能正常删除的项），与"坏的"那一个对比 DOM / 事件 / 结构 / 父子层级上的差异。
   - 差异点往往就是根因。一次只对比一组，别一次引入多个变量。

3. **先验证再修改**
   - 确认根因后再动代码；改完用同一对照组验证"对应项也变好了 / 没被改坏"。

4. **修完主动横向问**
   - 这个根因会不会影响别处的同类项？全局搜一遍同构写法，一起修，而不是等用户说"那边也一样"。

5. **生产无堆栈时，降级到开发模式复现**
   - release/打包构建的白屏崩溃往往没有可用堆栈（被压缩、被 ErrorBoundary 吃掉）。此时不要对着压缩产物猜——**切到 dev 模式（dev server / source map / 非压缩构建）复现同一路径**，拿到精确 `file:line` 的堆栈后再回生产验证。
   - **堆栈行号 vs 磁盘文件行号对不上 = 并发修改信号**：堆栈指向的代码和磁盘上读到的代码不是同一份（别的进程/会话正在改这个工作副本）。此时不要基于磁盘版本下结论，先确认"崩溃时那份代码"是什么，或改用与版本无关的根因（如"prop 为 undefined 必崩"这类不依赖行号的推断）。
   - 真实案例：`Cannot read properties of undefined (reading 'length')` 在生产构建里只有 ErrorBoundary 白屏；切 vite dev 复现后堆栈精确到 `ContextMenu.tsx:39:19`，且发现磁盘文件 39 行根本没有 `.length`——并发修改信号，改用版本无关的归因（items 为 undefined 时依赖数组求值必崩）做组件自防御修复。

6. **命令替换 `$()` 只该捕获"数据"，UI/提示必须走 stderr**
   - 触发：脚本交互菜单"反复打印 / 选了却报错 / 拿到的是提示文本而非你选的值"（如菜单循环、`SOURCE must be local or online` 即使输入 1）。
   - 根因套路：函数把菜单/提示 `printf` 到了 **stdout**，而调用方用 `$(...)` 捕获 stdout 当返回值 → 捕获的是一堆菜单文本，下游校验必然失败。这是 Unix 契约坑：**stdout 只承载机器可用的返回值，所有给人看的 UI 走 `>&2`**，否则任何用 `$()` 取值的调用方都会中招。
   - 判据与修复：函数里凡是"给人看"的输出（菜单、横幅、进度、调试）统一 `>&2`；只有最终选中的值 `printf '%s' "$ans"` 走 stdout。改完用 `"$var"=$(func)` 在真实终端复验一次。

> 真实案例：`envFrom` / 容忍度里点 ✕ 删不掉，最初被误判为"样式溢出遮盖"，反复改 CSS 无效。真正根因是这些删除按钮被包在一个 `<label>` 里（含 select + button），浏览器把点击转发给了 label 关联的表单控件，导致 `onClick` 未执行——是**事件层**问题，而非样式层。对比"能删的（普通 div）vs 不能删的（label 内）"后立刻定位。

## Part B —— 复用 / 抽象自觉

交付"功能正常"不够，还要主动做规律归纳：

1. **第 2 次重复就停**：复制粘贴到第二遍时，`grep` / 搜索统计同一模式出现几次；≥2 处就评估抽公共组件 / 函数 / 规则 / CSS 类。

2. **横向扫同类点**：改一处逻辑时，顺手搜全项目同构写法，把"这一处也会犯/也重复"的一次性覆盖。

3. **把复用当一等验收标准**：合并重复、收敛公共规则，与"修通 bug"并列，而不是可选项。

4. **抽完之后只剩一份定义**：以后调整行为（如行最小宽度、按钮样式）只需改一处，全局生效。

5. **样式调整要做"完整性核查"**：凡是改尺寸 / 间距 / 行高 / 字号 / 图标 / 圆角这类视觉属性时，用户往往只点出"第一个"（比如"这个行高太矮"），后续还有大量同类项。改完用户点名的那个，必须**主动横向枚举同布局 / 同类组件的所有实例**一起核对、一起调，而不是等用户一个个补：
   - 同一侧栏里：顶层项、分组标题、分组子项、集群项……所有可点击项的行高是否都保持一致。
   - 同一组件族：多个 tab / 卡片 / 按钮 / 表单字段的同类属性是否都是同一套值。
   - 复用 vs 独立：若已抽公共类（如 `.k8s-side-item`）改一处即全局生效——那就反过来确认**没被单独覆盖的"同层"样式**（如 `.k8s-top-item` 自己的 padding）也要一起更新。
   - 收尾时把"同类项清单"列给用户，让他们确认没漏。

6. **新增/复用网格布局时要核查"子控件可收缩性"**："能用"不等于"放得下"。容器（弹窗卡片/动态行/表格）内部的 grid 子项若不可收缩，内容会溢出容器，视觉上表现为"超窗 / 被截断 / 错位"。核查三件事：
   - **模板是否用了 `minmax(0, …)`** 而不是裸 `1fr`。裸 `1fr` 等价 `minmax(auto,1fr)`，子项最小宽度取内容 / 全局 `min-width`，撑不回去；`minmax(0,1fr)` 才允许真正压缩。
   - **是否有全局 `min-width` 压在子控件上**（如 `.input { min-width: 9.375rem }`）。即便模板写了 `minmax(0,1fr)`，子控件自己的 `min-width` 仍会逼轨道变宽；需要容器级兜底 `.container > .input { min-width: 0 }`。
   - **同一容器里的多控件是否同规则**（如 `宿主端口/容器端口/协议` 三控件共用一种可收缩模板）。
   - `grep` 该容器所在文件：`gridTemplateColumns: '1fr …'` 与 `'minmax(0,…) …'` 混用即嫌疑，纵向枚举同类容器一起改，别只修用户点名的那一个。
   - 真实案例：创建容器弹窗的端口映射三框裸 `1fr` + 全局 `.input{min-width:9.375rem}` → 拖出弹窗。而本项目另一处 RowList 早已用 `minmax(0,1fr)` —**这是"新模式里掺了旧写法"**：新写时参照了新模板，但落笔那几行还是一代旧写法。根因不在样式本身，而在"倒模时没核查落笔处是否真的用上了新约定"。

7. **"穿模/叠在一起"的另一个元凶是 `flex-shrink:1` 压扁子项但内容穿透**
   - 触发：多子项（树节点/卡片）展开后互相叠压、穿模，怎么调 key/overflow 都压不住。
   - 根因套路：容器是 `flex column`，子项默认 `flex-shrink:1`，内容多时子项被压扁到很小高度，但**子项内部内容（卡片/文本）本身不收缩、直接穿透到下层**——你看到的是"子项塌了但内容没跟着塌"。加 `overflow:hidden` 只是藏，补 key 无关痛痒。
   - 判据与修复：`display:flex` 容器里子项高度异常、内容溢出下层 → 先给子项统一 `flex-shrink:0`（或明确写 `flex: 0 0 auto`），让"要撑开的"真正按内容撑开。修完用脚本化几何测量（遍历子项 `getBoundingClientRect`，断言无重叠）验证，别只看截图。

8. **跨模块视觉对照：同角色控件的第二套实现 = 风格漂移 bug**
   - 触发：进入任何模块做审查/开发时主动做一次；或用户问"为什么 A 模块和 B 模块不一样"。**这类问题没有功能症状**——按钮照常能点、数据照常显示，症状驱动的 Part D/A/C 整条链都不会被触发，所以必须主动对账。
   - 原则：同一系统里，同角色控件（按钮/输入框/卡片/徽标）必须共用同一份视觉定义（单一视觉事实源）。出现第二套平台级实现（私有按钮类/内联样式/私有配色）即风格漂移。
   - 核查动作：
     1. **找基准**：全局标准控件类（如 `.btn`/`.input`）。grep 全项目 button 用到的类名分布——按钮语言 >1 套即开始对账。
     2. **跨模块 diff**：拿标准类的视觉值（背景/边框/阴影/圆角/字重/色彩来源）与私有类逐项对比。每条差异做三问裁决：走主题 token 吗？在所有主题（浅/深）下都存活吗？与兄弟模块一致吗？——三条全过 = 合法特例；任一不过 = 漂移，收敛回基准或升格为全局新基准（二选一，不许两套并存）。
     3. **主题盲检测**：grep 控件样式里的硬编码色（rgba 白/黑底、#hex 文字色、固定 blur/阴影）。它们不只是"风格问题"——换一个主题就是真实的可读性故障（深色底上的 `#333` 文字），要按 bug 处理。
   - 铁律：**风格漂移最擅长伪装成"设计特色"**。来历正当（当初专项有意做的玻璃拟态/赛博风）不构成豁免——裁决只看上面三条，历史正当性不是豁免权。
    - **案例会过期（纪律）**：本条及全 skill 的"真实案例"都是**历史快照**。引用前先花一句话核现状（`grep` 现值 / 跑一次脚本），**把已修的案例当活动缺陷报出来 = 制造假阳性**，比漏报更损伤报告可信度。实证：2026-09-18 两轮盲测**都**被这条过时案例牵走注意力，其中一轮专门花篇幅论证"该漂移已不成立"。
- 真实案例（**历史，已于 V13–V16 重构中修复**）：dbmanager 曾全部按钮走私有 `.btn-glass-soft`（50px 大黑影 + rgba 白底 + 3D 变换 + 硬编码 `#333` 文字色），主模块按钮是扁平 `.btn`。功能完好 → 数月无症状 → 直到用户跨模块对比"为什么这边的按钮有阴影"才暴露。**现状核对（2026-09-18 复核）**：`index.css:614` 的 `.btn-glass-soft` 已是纯主题 token 实现（`var(--surface)/--border/--text/--radius-sm`，无 box-shadow、无 3D、无 `#333`），全文件 `#333` 计数为 0 → **当前不存在该漂移，不要再把它当活动缺陷报出来**。

## Part D —— 排障前置假设核查（先验后归因，跨技术栈通用）

Part A 定位"症状在哪一层"、Part C 走完整根因闭环，但很多看似"代码 bug"其实**前提假设就错了**——源码本身损坏、代码写得对、但跑的不是那份代码、或跑的机器不对、或前提（环境/数据/目标）不成立。这部分把排障启动阶段必须核查的 6 类通用假设独立出来。**先验后归因**：不改代码前，逐条排除这 6 类，往往比直接改代码更快命中。

> 通用原则：**排障 = 先证伪前提，再归因代码。** 每次用户报"没生效 / 不对 / 重复 / 打错对象"，前 30 秒用下面清单问"前提成立否"，而不是冲去改代码。下面每条都给出**可移植到任何技术栈的核查动作**，案例仅作示例，不绑定具体栈。

### D0 源码/文件字节真实性（"编辑器看着正常 ≠ 字节正常"）

- **触发**：构建/编译失败（TS1002 / File appears to be binary / 中文乱码），或工具里显示正常但 build 就是报错；Windows 中文环境 + 中文注释场景尤其先验字节，再看逻辑。
- **铁律**：**编辑器/工具显示正常 ≠ 字节正常**——工具可能按系统默认编码（如 GBK）恰好解对了，掩盖了文件真实编码。
- **判定链**（先验字节，再看逻辑）：
  1. **无 BOM + UTF-8 解码无 U+FFFD + 按 GBK 反解可逆** → 单编码 GBK，可批量无损转 UTF-8。
  2. **出现"锟斤拷 / 浣犲ソ"类乱码** → 双编码（UTF-8 被误当 GBK 解码再存回），可逆还原。
  3. **每个中文字符串末字 + 闭合引号（`'`/`"`）被吞** → 有损损坏，不可逆，只能手工重写该串。
- **收口**：先确认"文件字节 = 我读到的源码"，再进 D1/D2；否则对错误字节的根因分析全是空转。

### D1 部署物漂移核查（"改了代码但跑的是旧的"）

- **触发**：用户报"我改过了怎么还这样 / 上次不是修了吗"。这是最高频假 bug 之一：源码已改、运行物没更新。
- **证据链**（任选可移植动作）：
  1. **字符串探针**：`strings <运行物> | grep -c "这次改动独有的唯一字符串"`，0 命中 = 跑的是旧物。（后端二进制同理；前端抓住产物 JS 的 hash/构建号/关键文案）。独特字符串必须是"旧版绝不可能有的"，否则探针会假阴。
  2. **hash/指纹对比**：对"由源码构建的新产物"与"运行中的旧产物"算 md5/sha256，不同 = 确实没部署新的。
  3. **时间戳与来源**：`stat` 产物 vs 最近 commit；运行物路径是否指向**仓库内另一份**（构建在 A、部署引用 B 很常见）。
  4. **构建链未走完**：编译成功 ≠ 已覆盖运行路径；检查 systemd/镜像/agent 的"工作目录/相对路径"是否让产物落了空位。
- **收口**：确认漂移后，重新部署 + 复跑探针验证命中；**建立"改一次部署一次 + 部署即校验"习惯**。

### D2 环境预检（"代码跑的机器/运行时对没对"）
- **复现环境必须隔离，且先剥离对外副作用**：用"独立实例 + 独立数据目录 + 错开端口"；
  **先摘掉会对外产生副作用的配置**（被管主机清单、通知 webhook、计划任务）。
  实例：为复现老版本起了个隔离实例，它读复制来的主机清单，**真的向 3 台生产主机推送并启动了 agent**——
  "只读复现"也会因为应用自身的启动行为写出副作用。剥离后再起，推送行数 = 0。


- **触发**：代码报了与进程/系统调用/挂载/权限相关的错；或同一功能本机能用、目标机不行；或脚本在有 `set -euo pipefail` 时报"没反应/卡住"。
- **核查顺序**（从外到内，先环境后代码）：
  1. **进程形态**：systemd 是否 PID 1？`/proc`、`/sys/dev/block`、`/dev` 存在且可读？（容器/精简环境会缺）——缺了则无数系统工具（`lsblk`/`df`/`mount`）都会假失败。
  2. **运行时身份**：`command -v` 实际命中什么？docker→podman shim、`df`→busybox 等兼容层会让"标准命令"行为/输出差异。
  3. **目标机形态**：区分"本机" vs "目标主机"——操作作用于哪台、配置文件在哪台，防止在 A 主机配了 B 才读的配置。
  4. **脚本护栏**：凡操作用 `set -euo pipefail` 的脚本，先审"失败的优雅降级"（`cmd && var=x` 陷阱、`read` 抢回显、`local x=$(cmd)` 吞返回码）。
  5. **独立通道对分（绕开被怀疑者直接测下一跳）**：报错来自某个应用时，**用最简独立客户端直连同一目标**（curl / nc / python 单行连库 / 裸 TCP），把"服务端坏了"和"客户端配置错"切开。独立通道连通 = 服务正常，问题在出事应用侧的配置/环境；独立通道也失败 = 服务端/网络问题。这一刀下去，一半的可能性直接被排除。真实案例：dbx 报 MySQL "Connection refused"，用 pymysql 直连 3306 成功且列出全部库 → 服务完全正常，问题在 dbx 进程的运行环境（后由 D5 的错误码取证定位到容器）。
- **收口**：环境问题先用"已被证实的正常环境对照"确认，再谈改代码。**AGENTS/环境差异规则**应前置——动手前列出目标机形态再动手。

### D3 数据完整性对账（重复 / 覆盖缺口 / 空数据）

- **触发**：列表出现重复项、某列某指标永远空、切数据源后内容错乱。
- **三把尺**（全可移植）：
  1. **唯一性对账**：对响应/结果集跑 `统计唯一键数 vs 总数`——两者不等 = 有重复，定位到具体重复实例（如 `atd.service ×2`）。归因到"追加逻辑没做 ID 去重"。
  2. **覆盖矩阵对账**：多路采集/多套实现（本机 / agent / SSH / 不同源）时，列一张"横切面字段 × 每路是否含"矩阵——空单元格就是覆盖缺口。矩阵比人肉记更容易漏。
  3. **空数据归因**：别只看到"空/无数据"，追到赋值处（硬编码空数组? / 解析字段名大小写不匹配?），用最小请求把"是前端没展示还是后端没给"切开。
- **收口**：数据缺陷常与 D1（部署物漂移）/D4（缓存/增量残留）叠加，先证数据对错，再证展示对错。

### D4 目标对象身份 & 状态残留（作用到对的人/物，增量是否归零）
- **状态作用域 vs 视图身份**（多标签 / 多视图 / 多租户场景必查）：**state 的作用域粒度必须 ≥ 视图身份粒度**。
  实例：查询标签按 `connId.db` 分 tab（视图身份细），但 `result` 是模块级**单份** state（作用域粗）→
  在 A 库标签执行查询，切到 B 库标签仍显示 A 的结果。查法：先列出"视图身份由哪些 key 组成"，
  再逐个确认对应 state 是否也按这些 key 分隔（是 map 还是单值）。


- **触发A（打错对象）**：多主机/多连接池时，操作球结果作用于**没点选的那台**。核查：操作链路里 target/连接标识是否真被赋值并沿调用链传递（而非默认/兜底到 A 主机其后端硬编码）；在**目标对象上**验证结果（`.11` 上查 daq devil 状态真变没有），而非只信返回的 ok。
- **触发B（状态残留）**：增量追逻辑/缓存跨"数据源、视图、筛选"切换不重置——如把 access 的行号用去过滤 error 的新内容、切换视图沿用上回 `lastNum`。核查：任何**跨边界复用的"游标/已见集/缓存路径"**，在切换边界处是否归零；边界包括数据源、模块、主机、筛选条件。
- **触发C（有状态资源被池化 → 状态漂移）**：凡"连接/会话"类**有状态资源**被池化复用（数据库连接池、SSH 池、HTTP keep-alive），只在单个资源实例上成立的假设（`USE db`、`SET` 变量、临时表、未提交事务、登录态）会在**下一次借出时漂移到别的实例**——表现为"上一句设置的上下文，下一句就丢了"。核查：症状是"上下文丢失/时有时无"时，先问"这个资源被池化了吗"；修复优先找**库内现成的"钉住"机制**（把有状态操作钉到同一物理实例，如 Go 的 `SessionExecerProvider`、驱动级 `conn` 单连接），复用而非自造；实在没有再退化为"把状态并入每条语句"（如显式 `db.table` 全限定名）。
- **收口**：三害同源——**"谁"、"上次的假设"、"哪个资源实例"**没在边界处重新断言。对比"能正确的工作路径"与"错乱路径"，差异点往往就是没归零的那个游标，或没钉住的那个池化连接。

### D5 错误文本取证（错误消息本身就是证据）

- **触发**：拿到任何带错误码 / 错误前缀 / 平台特征的报错时，**先读错再动手**。错误文本的每个成分都在回答"谁在报错、在哪一层报错"。
- **三个取证维度**（全可移植）：
  1. **平台特征错误码定位运行环境**：操作系统错误码是平台指纹——`os error 111` 是 Linux 的 ECONNREFUSED（Windows 会是 10061）、`errno 13` 是 Linux EACCES（Windows 是 5）。**报错文本里出现"非当前平台的错误码" = 报错进程不在你以为的机器上**（在 WSL/容器/远端）。这一条曾直接把"MySQL 连接拒绝"从服务端问题反转成"客户端进程跑在服务器上的 Docker 容器里、连 localhost 连到了容器自己"。
  2. **服务端语义错误码定位故障层**：数据库/中间件的错误码有精确语义——MySQL `1130`(主机未授权)/`1045`(密码错)/`1046`(未选库)/`1046 3D000`(会话无库上下文)，PG `28P01`(密码认证失败)/`42P01`(表不存在)/`3D000`(库不存在)。同样表现为"连不上"，1130 说的是网络可达但被拒授权、1045 说的是凭据错——**先查码表，别把语义不同的错混为一谈去修**。
  3. **报错来源前缀定位报错者**：`pymysql.err.` / `go-sql-driver:` / `sqlx:` / 应用自定义 message 格式——谁的名字出现在前面，谁就是报错方；报错方 ≠ 故障方（客户端经常替服务端传话，反之亦然）。
- **收口**：错误取证常与 D2.5（独立通道对分）连用——错误码负责"指向嫌疑"，独立通道负责"证实/证伪"。两步做完再归因代码，多数连接/环境类报错不用看一行业务代码就能定位。

### 收尾：Part D 与 A/C 的配合

- 三步依序：**D 前提核查（30s 快筛）→ A 层级二分 → C 完整闭环**。
- 命中 D1/D2 时**先别写代码**——先重部署/修环境，复验探针，多数这类"bug"根本不是代码问题。
- 快速检查清单增加：
  - [ ] 源码文件字节是真实的吗？（编码真实性：无 BOM+UTF-8 无 U+FFFD+GBK 反解可逆 / "锟斤拷"类双编码可逆 / 末字+引号丢失不可逆）
  - [ ] 跑的是不是最新产物？（strings/hash/时间戳探针）
  - [ ] 代码运行的机器/运行时/挂载形态对不对？（environmental preflight）
  - [ ] 数据有没有重复 / 覆盖缺字段？（唯一性 & 覆盖矩阵对账）
  - [ ] 操作作用到目标对象了吗？增量游标/缓存跨边界归零了吗？有状态资源被池化、上下文会漂移吗？（目标身份 & 状态残留 & 池化漂移）
  - [ ] 错误文本取证了吗？平台错误码是否指向另一个运行环境、服务端错误码语义是否查过、报错者是谁？（D5）

## Part E —— 高频根因速查（脚本 · Windows · 布局 · 运行时）

**什么时候该把一条规则变成脚本**：判据只有一句——**它是不是"读一遍就懂，然后就没然后了"**。
散文形态的规则会被降级成"验证它举的例子"（实证：E13 改造前两轮盲测都这样漏过；改造后，agent 立刻跑起脚本并在浏览器里复现出问题）。

**机械化的验收（别跳过）**：新脚本必须做**双面验证**——在"已知有该问题的版本"和"已知已修的版本"上各跑一次，
**两次结果必须不同**（例：`清除筛选` 在修复前只有 门控/菜单型 入口，修复后出现 `常驻候选`）。
跑不出差异 = 这个脚本没有区分力，等于没写。


下面这些是从多轮真实排查里提炼的"一报就怀疑它"的根因，命中即优先检查。每条都是通用规则，平台/框架只是示例。

**E1. 命令替换 `$()` 捕获了 UI 而不是返回值**（→ 详见 Part A.6）
症状：脚本菜单循环 / 选了却报错 / 拿到提示文本。规则：UI 走 `>&2`，stdout 只承载返回值。

**E2. `flex-shrink:1` 压扁子项但内容穿透下层**（→ 详见 Part B.7）
症状：多子项展开后互相叠压穿模，调 key/overflow 无效。规则：flex 容器子项统一 `flex-shrink:0`，用脚本化 bbox 测量验证。

**E3. 渲染主流程被非关键代码抛错中断**
症状：加了某个增强（hover/tooltip/图表提示）后整个页面或面板不渲染 / 白屏。
规则：凡"增强型"代码（非主数据流），先 try/catch 包裹 + 容器补 id；任何 `xxx.appendChild`/`.length` 对可能为 null/undefined 的对象都要兜底。根因：`$("#dChart")` 为 null 一抛错，后续 render 全断。与 Part A.5 / D4 的"组件自防御"同一纪律。

**E4. 平台能力不满足时，换宿主框架优于继续打补丁**
症状：透明 + 可点击 / 命中区 / 分层窗口等"平台层"能力反复修不好（补丁轮番失效）。
规则：先判断这是"业务 bug"还是"宿主框架能力缺陷"。pywebview 透明命中区 bug 打了 4 次补丁无效 → 迁 Electron（原生透明）一次解决。同类：**"服务/任务反复被改回某状态"先查是否自己创建了循环计划任务/定时器**——自查自己的 plan/脚本产物，别总怪外部。

**E5. OS 级异常诊断：事件日志时间线 + 系统性排除 + 先懂平台架构**
症状：机器异常（意外关机/重启/断电），且"用着突然发生"。
规则（三步）：① 用系统事件日志重建"开机/关机时间线"（如 Windows `Get-WinEvent` 找 41/6008/6006/1074），区分意外断电（无 6006/1074 前置）与正常/计划；② 列排除清单逐项证伪（计划任务 / 更新 / 蓝屏 BugcheckCode / 硬件 WHEA / 电池）；③ **先懂平台架构再归因**（`powercfg /a` 分清 S0 现代待机 vs S3），"无日志本身"在排除完其他项后就是证据（硬件级断电不留日志）。

**E6. Windows 高频三件套**
- **中文/非 ASCII 路径**：MSVC/老工具链不认 `E:\代码`，报错文件名乱码是判据 → 项目搬纯英文路径再构建。
- **无扩展名二进制 + `/` 前缀**：PowerShell 不认无 `.exe` 的命令、`/cmd` 是 Linux 写法 → 复制出 `.exe` 用完整路径。
- **端口被占**：服务起不来/连不上 → `netstat -ano` 找监听 PID → 反查进程名（可能是输入法/浏览器等无关程序占了端口）→ 释放或换端口。

**E7. `.gitignore` 目录规则不锚定会误吞源码**
症状：本地某目录文件"提交不进去"或"大量未跟踪"。
规则：`src/` 不带 `/` 会在任意层级匹配（`web/src`、`third_party/.../src` 全被忽略）；要精确锚定目录写 `/src/`。用 `git check-ignore -v 路径` 验证是哪条规则命中。

**E8. flex 高度链断裂 → 内容落到外层滚动容器（"底栏按钮看不见/内容被截"）**
症状：区域底部按钮或内容被推出视口，滑块却在页面而不是区域里。
规则：查完整祖先链的 flex 三要素：`flex:1 / min-height:0 / overflow` 每层齐不齐；容器 `overflow:hidden` + 固定段 `flex:none` + 可滚段 `flex:1; min-height:0`，底栏按钮放可滚段之后即常驻。→ 完整方法：`references/ui-layout-debug-method.md`

**E10. 前后端对不上：占位端点 + 状态源脱节 + 触发路径缺失（三联征）**
症状：UI 提示"请去 X 界面做 Y 操作"，但 X 界面没有对应按钮；或按钮点了没反应/状态永远不变；而路由表里明明"有"这个接口。
三联征逐一排查（真实案例：驱动"安装启用"——路由存在但 handler 是 501 stub，installed 状态字段与安装动作写的是两个不同来源，前端按钮根本没渲染）：
1. **触发路径**：UI 上每个写操作按钮是否真的渲染（条件分支里被吞=动作静默死亡，报错永远不会出现）。
2. **端点真实性**：路由表里全部**写操作端点逐个 curl 冒烟**——501/TODO/"开发中"stub 是高发区（写代码时建占位忘实现）。
3. **状态源对齐**：UI 展示的状态字段与写操作修改的字段必须**同一来源**；两个来源并存（如"构建包含"vs"标记文件"）= 自相矛盾态（"未安装"徽标与已写安装标记并存）。
预防：功能交付前跑一遍"动作清单 E2E"——UI 每个按钮/动作端到端触发一次（或 curl 等价调用），stub 现形即登记。

**E9. 按钮/控件缩小后四周留白不对称（压缩未连带行高/老样式残留）**
症状：按钮变小了，周围空着一圈，离上下距离不一致。
规则：几何量化（`getBoundingClientRect` 量 top gap vs bottom gap）→ 样式考古（同一选择器历史多段定义逐块比对属性，老块 `margin-bottom/padding` 残活是隐形根因）→ 统一按钮定高（`height+line-height` 等宽），容器 `padding` 双端等值单点控留白。→ 完整方法：`references/ui-layout-debug-method.md`

**E11. 重叠/溢出与尺寸核算：先量矩形数字，再猜原因（视觉验证"测量不目测"）**
症状：表单输入框互相叠压 / 字段被盖 / 下拉压住后续控件；"看着是贴在一起"。
规则：凡是"疑似重叠/溢出"的布局症状，先取矩形数字判定，再谈根因——
用 `getBoundingClientRect()` 两两求交：`ox = min(a.right,b.right)-max(a.left,b.left)`、`oy = min(a.bottom,b.bottom)-max(a.top,b.top)`，`ox>4 && oy>4` 即真重叠（阈值 4px 滤掉边框/阴影噪声）；用数字反推"谁溢出了多少"再定位到具体元素。
必查的四个高发模式：
- **定宽容器 + `w-fit`/inline-block 子元素**：fit-content 在 inline-block 上取 max-content 尺寸，不收缩 —— 内容宽 > 容器宽时溢出压住后续兄弟（真实案例：`div.w-40` 包 HostSelect trigger，w-40=10rem 受根字号缩放、trigger 内容 159px > 容器 126px，溢出 26px 覆盖下一输入框；修法 trigger 改 `w-full`）。判定公式：`容器宽 ≥ 子元素内容 max-content 宽` 不成立即溢出。
- **rem 陷阱**：`w-40` 类固定 rem 宽度会随根字号缩放；同一布局在不同设备（16px vs 缩放根字号）表现不同 —— "标准机器不复发"不等于没 bug。排查时必须量 `getComputedStyle(document.documentElement).fontSize`。
- **flex-wrap 掩盖**：`flex-wrap` 让溢出行换行，视觉无害；一旦容器加宽/减少字段使行不再换行，被掩盖的溢出立即暴露。改布局尺寸后要反查"之前被换行掩盖的行"。
- **环境敏感必查**：根字号、视口宽度、缩放（`devicePixelRatio`/`zoom`）三者差异足以让同一个 bug 只在特定机器出现。
收尾纪律：布局/表单改动验证 = 几何测量（脚本跑两两相交检查），不是看截图"觉得没问题"；同类表单弹窗全跑一遍同一检测。
→ 与 E8/E9 同族；延伸方法：`skills/project-cartographer/references/ui-layout-debug-method.md`（几何量化/统一度量）

**E12. CSS 变量引用了不存在的名字（深色主题下发白 / 圆角变直角 / focus 无边框）**
症状：某卡片在深色主题下仍是白底、某圆角失效、focus 没边框、hover 没背景 —— 且**只在特定主题或特定元素上出现**，同一份样式在别处却正常。
规则：`var(--x, fallback)` 中 `--x` **从未定义**时，浏览器不报错、**永远走 fallback**：
- **有 fallback** → 静默用固定色 → 深色主题下不协调（如 `#eef2ff` 浅蓝配深色底）
- **无 fallback** → **整条声明失效**。最危险的是 `rgba(var(--danger-rgb), .08)` 这种：不是某个属性失效，而是**整个 `background` 没了**
一键排查（脚本跑差集，别靠肉眼扫 CSS）：
`python scripts/audit_styles.py --root <前端源码目录>`
做法：提取全部 `var(--x)` 引用 与 全部 `--x:` 定义，做集合差集，按「无 fallback / 有 fallback」分级输出（**变量名精确匹配，结论可直接采信**）。
三种高发根因：
1. **"以为变量存在"**：文件注释明写"复用项目既有变量 `--panel`"，而该变量全项目零定义（作者沿用了别的项目命名）→ 6 处引用全靠 fallback 硬撑，其中 1 处 toast 变成"白底浅字"根本看不见。
   → **注释写的意图 ≠ 实际存在的变量。以 `grep -- "--x:"` 的结果为准。**
2. **名字记错**：`--font-mono`→`--mono`、`--dim`→`--text-dim`、`--primary`→`--accent`、`--radius`→`--radius-md`、`--err`→`--danger`。修法：全项目 grep 同类变量名，用**已存在的**替换。
3. **不存在的 `-soft`/`-bg` 变体**：项目只有 `--accent`，没有 `--accent-soft`/`--accent-border` → 改用 `color-mix(in srgb, var(--accent) 12%, transparent)`（若项目已在用 `color-mix`，风格保持一致）。
修复优先级：**无 fallback 的先修**（样式已在失效）；有 fallback 的先判断 fallback 是不是**刻意的固定色** —— 深底亮字的结果提示条（如 `#0a2e1a` 配亮绿字）往往是有意设计，改成 `color-mix` 反而会降低对比度，**改前先问**。
→ 脚本：`scripts/audit_styles.py`（泛化版，支持 `--root`）。**它同时标注了可靠性分级**：变量名匹配属高可靠；而"裸控件/兜底继承"这类结构判定**低可靠**（行扫描判不准 DOM 层级，会把兄弟元素当祖先），必须人工核实后才可采信。

**次生灾害（必查，比原缺陷更严重）**：失效声明常与**同一规则里的另一条有效声明**组合出更坏的后果。
实例：`.db-edit-input:focus { outline: none; border-color: var(--primary) }` —— `outline:none` **有效**、
`border-color` 因变量不存在**失效** → 两者叠加 = **键盘焦点完全不可见**（比"边框色失效"重一个量级）。
→ 修 E12 时先看同一规则里有没有 `outline:none` / `border:0` / `background:transparent` / `box-shadow:none`
这类**剥夺回退视觉**的声明；有就把该条提到最高优先级（可访问性级）。


**E13. 交互点在特定状态下不可达（"功能在，但碰不到"）**

症状：某按钮/菜单项"找不到"或"点不到"，但代码里明明有；**只在特定数据或状态下发生**；报"只能刷新页面才能恢复"。

**① 工具先行（把 E13 从叙述变成动作）**

```bash
python scripts/audit_escape_entries.py --root <前端源码目录> --out escape-report.md
```

它把「清除 / 取消 / 返回 / 刷新 / 重置」这些**逃生动作**的入口按族列全，标注每个入口的性质（**常驻候选 / 门控 / 菜单型**），并生成待填的「入口 × 四状态」矩阵。
**为什么必须机械化**：E12 之所以每次都被抓到，是因为它是"一条命令 + 一张表"；E13 之所以总被漏，是因为它只是一段案例叙述。叙述会被读成"我懂了"，命令才会真的被执行。

**② 逐入口 × 逐状态对照**（四类状态，每格问三句：**在 DOM 里吗？够得着吗？动作还成立吗？**）

- **零行 / 空结果**：依赖行内元素的入口（单元格右键、行右键、行内按钮）**全部失效**——没有目标可点。
- **查询出错（数据为 null）**：被 `xxx && data` 门控的 UI **整块消失**（连里面的"取消/清除"一起没了）。
- **超宽内容**：`colSpan={全部列}` + `textAlign:center` 的占位会被推到表格水平中部 —— 实测 51 列下按钮位于 `x≈3505`、视口仅 1700px，**功能正常但人在视口外够不着**。修法：把空态渲染到 `<table>` **之外**（宽度跟随容器而非列宽），别塞进 `colSpan` 的 `<td>` 里。
- **门控未开（默认折叠/隐藏）**：`useState(false)` 折叠起来的条件栏、藏在二级菜单里的入口 —— **用户根本不知道它在那**。

**③ 判门控性质**：`{showFilterRow && data && ...}` 要分清"依赖**数据内容**"还是"只依赖**开关**"——内部要用 `data.columns` 的，去掉 `data` 门控会直接崩，**不能盲目放宽**。改法是给逃生动作**另加一个常驻入口**，不是拆掉门控。

**五条纪律（都来自真实翻车）**

1. **禁止只验证本条目的例子。** 实例：某轮体检 agent 把 E13 读成了"超宽表空态"一个子情形，查完 `colSpan` 没问题就写下"E13 ✅ 健康"，而**同一模块"零行 → 清除筛选无入口"原样躺着**。**例子是例证，动作才是验证对象。**
2. **任何"清除/取消/返回/重置"这类逃生动作，必须存在一个不依赖数据状态的常驻入口。**
3. **判定单位是「具体动作」而非关键词族**——`清除筛选` 和 `清空表` 同属"清除"族却是两件事，别拿族级数字给自己虚假安慰。

**真实案例（2026-09-18，opscore dbmanager —— 已按代码复核修正过一次）**：右键单元格「按此值筛选」→ `onFilter` **静默应用筛选**（`DataPanel.tsx:326` 只 `setFilters` + `setPage(1)`，**不打开过滤行**）→ 结果是 0 行，而**界面上没有任何"正在筛选"的指示**。此刻清除筛选的两条路：
  - ① `DataGrid.tsx:187` 的右键菜单项「清除全部筛选」——**零行时没有行可右键 → 真不可达**；
  - ② `DataPanel.tsx:283` 的「清除全部」按钮——在 `{showFilterRow && data && (` 门控栏里，**但它上层的开关（`DataPanel.tsx:243` 的「过滤行」toggle）是常驻的** → **严格说不是"不可达"，而是"可达但要两跳 + 按钮名不含清除语义 + 全程无筛选指示"** → 用户找不到，报「清不掉，只能刷新」。
  - ⚠️ **教训**：初版案例写成"一个不可见、一个不可达"，**把"不可发现"当成了"不可达"**，后来的复核 agent 花了一整节去"纠正文档" —— **案例描述不精确 = 让下一个人替你还债**。
  - → 由此补出两条更细的纪律：**④ 区分「不可达」（没有目标元素 / 被门控）与「不可发现」（可达但要几步、且无状态指示）——两者都算 bug，但修法完全不同；⑤ 凡"改变状态"的动作（应用筛选 / 排序 / 分组 / 锁定 / 切换视图），必须同时给出 ①可见的状态指示（chip / 徽标 / 计数）②就近的清除入口。只 setState 不给指示，用户就进入了一个"看不见的筛选状态"——这才是本案例真正的根因。**

→ 与 E10 `showFilterRow` 门控同族；状态边界的通用方法见 `skills/project-cartographer/references/runtime-verify.md` 二·七（**状态边界 ≠ 中间态**）。

## Part C —— 完整根因闭环（委派给 systematic-debugging）

Part A 解决的是「点了没反应」这类**外在症状的快速判断**。当问题复杂、涉及多层组件、或已尝试 2 次以上修复无果时，应进入更严谓的**根因闭环**：

> `debug-and-refactor` 专注**「判断定位」**；`systematic-debugging` 专注**「验证复现 + 最小试验 + 归档测试」**。

复用 `systematic-debugging`（位于 `function-specific/misc/superpowers/systematic-debugging`）的 4 个阶段：

1. **Root Cause Investigation** — 读完整错误信息、反复复现、查最近改动、多组件时在每层加日志埋点。
2. **Pattern Analysis** — 找工作的同类对照，详读参考实现，列出全部差异。
3. **Hypothesis and Testing** — 表单单假设、最小化改动、一次一变量、不能盖过再上。
4. **Implementation** — 先写 **failing test** 再修；单一变更；验证后才收工。
   - 若 **3 次以上**修复均失败 → **停止并审视架构**（而非继续猜修）。

**进入 Part C 的触发条件：** 问题非单次点击加删，而是多组件串联 / 多次试验 / 环境差等。

- 触发时直接调用：`/systematic-debugging`
- 参考：`superpowers:test-driven-development` 写回归测试；`superpowers:verification-before-completion` 收尾验证。

> 真实场景联动：`debug-and-refactor` Part A 「事件层 vs 样式层二分 + 最小对比」，在判断为「事件层」后，可直呼 `systematic-debugging` Phase 2「找同类对照并比较差异」作为深入；判断为「样式层」后，本身已包含最小对比，无需额外闭环。

## Part F —— 仓库/产物损坏自救（对象缺失 · ref 丢失 · index 损坏）

**症状信号**（命中任一）：`fatal: not a git repository`（但 `.git` 明明在）· `bad tree object <sha>` ·
`invalid object 100644 <sha> for '<path>'`（write-tree/commit 失败）· `fetch` 报 `old..new main -> origin/main`
但 `rev-parse origin/main` 仍是旧值 · 提交显示成功、下一个命令却说"还没有提交"。

**元凶常常是自动维护被中断**：`geometric-repack` / `pack-refs --prune` 失败会留下
"对象缺失 + ref 被 prune 空 + packed-refs 陈旧"的半成品（典型报错 `error: failed to perform geometric repack`）。
**第一步先止血**（仓库级，不动全局）：

```bash
git config maintenance.auto false && git config gc.auto 0 && git config maintenance.strategy none
# 另外去任务计划程序查有没有 Git Maintenance 定时任务
```

**诊断三连（按序）**

1. **仓库还认不认**：`git rev-parse --is-inside-work-tree` 失败 → 多半是 `.git/refs/` 没了（git 校验 git-dir 要求它存在）：
   `mkdir -p .git/refs/heads .git/refs/tags .git/refs/remotes/origin`
2. **对象缺多少**：`git fsck --no-progress | grep -c '^missing'` —— ⚠️ **它只检查 ref 可达的对象**。
   要覆盖远端最新提交必须 `git rev-list --objects <远端tip> | awk '{print $1}'` 求交集。只看 fsck 会得出"0 缺失"的**假结论**。
3. **ref 写没写进去**：`update-ref` 报成功但值不变 → 先查**父目录是否还在**（`.git/refs/remotes/origin/` 被删过就会出现静默失败）。

**抢修动作**

- 补对象：`git fetch --refetch --no-tags origin main`（强制全量重下，git ≥ 2.36）。
- 补 ref：`git update-ref refs/heads/main <本地tip>`、`git update-ref refs/remotes/origin/main <远端tip>`（loose ref 覆盖陈旧的 packed-refs）。
  ⚠️ **先 `mkdir -p .git/refs/remotes/<远端名>`**：该目录缺失时 `update-ref` 会**静默失败**（退出码 0、无任何报错、值不变）。
  实证（2026-09-18）：`git update-ref refs/remotes/origin/main <sha>` 连试多次都是旧值，原因是 `refs/remotes/origin/` 被
  "空目录清理"反复删掉了；`mkdir -p` 之后同一条命令立刻生效。同理，`fetch` 报 `old..new main -> origin/main`
  却查不到新值，也是这个原因，不是网络问题。
- 重建 index：`mv .git/index .git/index.corrupt-<日期>` 再 `git add -A`。⚠️ **空 index 下 `add -A` 会跳过"被 .gitignore 忽略但已被跟踪"的文件**
  —— 必须先确认 `git status` 里没有意外的 `D`（删除），漏掉的要 `git add -f <文件>` 补回。
- 物化工作区：`git -c core.longpaths=true reset --hard <tip>`，**循环重试直到「磁盘文件数 == 树内文件数」**——一次写不全很常见。
- 校验三连（缺一不提交/不推）：`git write-tree` 能出树 · `git fsck` 可达 missing 为 0 ·
  `git diff --name-status <远端tip> HEAD | grep -c '^D'` **必须为 0**。
- 推送：`git push origin <sha>:refs/heads/main`（**用 sha 不用 ref**，绕开本地 ref 不可靠的问题）。

**四条坑（都真踩过）**

1. **判断"谁更新"不能信本地 ref**：本地 `origin/main` 可能卡在陈旧的 `packed-refs`；只信 `git ls-remote` / `git push --dry-run`。
2. **`reset --hard` 的输出绝不能 `tail`**：错误行夹在 `Updating files:` 进度里，截断后就看不见"只写出 444/2000 个文件"
   —— 后续 `add -A` 会把漏写的文件全部记成**删除**。
3. **破坏性提交前断言"staged 删除数 == 0"**，推送前再断言"与远端 diff 的删除数 == 0"。
4. **动仓库前先整目录备份（含 `.git`）** —— 这次能无损恢复全靠它。

## 快速检查清单

动手前 / 收尾前过一遍：

- [ ] 症状类 bug：先判**事件层还是样式层**？
- [ ] 是否建立了**能 vs 不能**的最小对比？
- [ ] 改前是否**确认了根因**（而非试样式）？
- [ ] 非单次点击就能解决吗？**否则触发 Part C → systematic-debugging**。
- [ ] 是否 `grep` 过**同类重复**（≥2 就考虑抽公共）？
- [ ] 修完是否**横向覆盖**了所有同类点？
- [ ] 是否**只剩一份**公共定义（删除重复）？
- [ ] 样式调整是否做了**完整性核查**（横向枚举同布局所有同类项一起调，非只改用户点名的一个）？
- [ ] 本模块的按钮/输入框/卡片用的是全局标准类还是私有类？跨模块对照过吗？硬编码色在别的主题下会坏吗？（B.8 风格漂移——无症状，须主动对账）
- [ ] **逃生动作（清除/取消/返回/重置/刷新）是否都有「不依赖数据状态」的常驻入口？** 跑 `scripts/audit_escape_entries.py`，逐个入口 × 四状态（零行 / 出错 / 门控未开 / 超宽）对照过吗？（E13 —— **禁止只查它举的超宽例子**）
- [ ] **仓库/产物异常**（`not a git repository` / `bad tree object` / 提交成功却消失 / fetch 报更新但 ref 不跟着动）→ 走 **Part F**
- [ ] 涉及容器/弹窗/动态行的网格布局：是否用了 `minmax(0,…)`、子控件是否被全局 `min-width` 顶住、有无 `min-width:0` 兜底？（裸 `1fr` = 溢出高危）
- [ ] **前提假设核查**（Part D，改代码前先过）：源码字节真实 / 跑的是最新产物 / 环境形态对 / 数据无重复缺口 / 目标对象与增游标正确？
  - 是否验过文件字节真实性（编码真实性判定链：单编码 GBK 可逆 / "锟斤拷"双编码可逆 / 末字+引号丢失不可逆）？
  - 是否用 strings/hash/时间戳验过运行物 = 源码？（部署物漂移）
  - 是否确认过机器/运行时/挂载形态？（环境预检）
  - 是否做过唯一性 & 覆盖矩阵对账？（数据完整）
  - 操作结构作用于目标对象？跨边界游标/缓存归零？有状态资源（连接/会话）被池化、上下文会漂移吗？（目标身份 & 状态残留 & 池化漂移）
  - 是否先读了错误文本？平台错误码 / 服务端语义码 / 报错者前缀分别指向什么？（D5 错误取证）
  - 生产构建无堆栈时，切 dev 模式 + source map 复现拿堆栈了吗？（Part A.5）
  - 命中脚本/Windows/布局/运行时的"高频根因速查"了吗？（Part E：`$()` 契约 / flex-shrink 穿透 / 渲染单点抛错 / 换框架 / 事件日志时间线 / Windows 三件套 / gitignore 锚定）

## 使用方式

- **改代码之前**：先跑 Part D 前提核查（源码字节对吗 / 跑的是最新产物吗 / 环境对吗 / 数据对吗 / 目标对吗），多数"假 bug"在这里解决。
- 用户报症状类 bug → Part D 快筛后按 Part A 快速判断；复杂/多次失败 → Part C 交付 `systematic-debugging` 闭环。
- 改动 / 新增代码 → 按 Part B 主动识别重复并复用。
- 收尾前跑一遍"快速检查清单"。
