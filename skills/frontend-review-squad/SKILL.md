# 前端审查小分队 (Frontend Review Squad)

你要做的事情本质上只有一件：**领一次多视角的前端审查，产出一份"每条带证据"的分级问题清单，并在修复后做回归**。

九个成员各管一段，你是指挥。**不要把九个 skill 各自跑一遍**——那是九倍的 token 换八成的重复。按下面的分工矩阵和执行顺序走一遍，每个成员只出它独有的那份检查。
**开工前先做成员可用性自检**：逐个确认成员 skill 是否存在——**必须递归搜**（`find skills -iname "*<成员名>*" -name SKILL.md`），**禁止只查顶层目录**（顶层没有 ≠ 不存在，本仓库 300+ 个 skill 下沉在 `function-specific/` 里）。找到的**写上解析到的真实路径**；**只有递归搜过仍找不到，才允许列为覆盖缺口**，且必须写清搜索命令与范围。**不许假装执行过**；能用现有成员替代的写清替代方式。

## 成员与分工矩阵

| # | 成员 | 在小分队里的角色 | 独有检查（别的成员不查） |
|---|---|---|---|
| 1 | `project-cartographer` | 侦察兵 + 闭环测绘 | 交互点→后端函数水流；双向映射（🕳️ 后端有前端没接 / 🪝 前端调了后端没有）；孤儿 API 反查；形态牌（morphology-probe） |
| 2 | `debug-and-refactor` | 前提核查 + 工程体检 | **D1 部署物漂移（审查对象=运行产物还是源码？）**；D0 乱码注释/编码事故；重复定义与死代码（CSS/TSX）；复用审计（Part B：同构写法 ≥2 就该抽公共）；高频根因速查（Part E） |
| 3 | `workbench-layout` | 工作台布局硬规则 | z-index 预算（工具层 10 / 浮层 ≥150 / 全屏遮罩 ≥200）；sticky 表头单滚动容器；右键菜单 flip；split-view 收缩抖动 |
| 4 | `layout-guardrails` | 溢出守门 | grid/flex 子控件可收缩性（裸 `1fr` / 全局 min-width 顶开 / flex-shrink 穿透）＋ **塌缩盲区：flex-basis:0 在 grid 行高 auto 时压塌行高→内容被 overflow 裁掉=「压缩饼干」症状；flex-basis: auto 才是等高安全默认**；触区尺寸；**运行几何核验：等高块必须用 boundingBox 量 clientHeight vs scrollHeight，不能只读 CSS**；等高失效（grid 行高 auto 时 flex-basis:0 压塌→内容被裁） |

| 9 | `impeccable` | 审美总裁判 | 以其 Operate 模式判总：可扫读性、一致性、真实使用场景优先于表达——用于裁决"改不改"的优先级 |

**⚠️ 成员路径与定位纪律（必须先读，否则会误判"成员缺失"）**

本仓库的 `skills/` 是**两层结构**：顶层是散装 skill，另有 3 个**下沉包**——
`function-specific`（内含 300+ 个 skill）、`framework-specific`、`platform-specific`。
**递归共有 400+ 个 `SKILL.md`**，而顶层只有 70 多个目录。

上表 9 个成员的真实位置：

| 成员 | 真实路径 |
|---|---|
| `project-cartographer`、`debug-and-refactor` | `skills/<成员名>/SKILL.md`（顶层） |
| `workbench-layout`、`layout-guardrails`、`design-taste-frontend`、`make-interfaces-feel-better`、`ui-ux-pro-max`、`hallmark`、`impeccable` | `skills/function-specific/frontend/<成员名>/SKILL.md`（**下沉**） |

**定位三律**：
1. **只用裸名字在顶层找 = 假阴性**。真实事故（2026-09-18）：一轮盲测因为"顶层没有 `hallmark/`"就判定 7 个成员全缺、整步跳过——它们其实一直躺在 `function-specific/frontend/` 下。
2. 正确做法：`find skills -iname "*<成员名>*" -name SKILL.md`（**递归**）；找不到再换关键词。
3. 取用前先查 **`find-skills` 的路由表**——它已用「**下沉：<路径>**」标注了这类 skill；`skills/INDEX.md` 也按层登记。

机械统计是 Step 2 的地基，用脚本扫全文件而不是逐文件读：**重复选择器数、字号/圆角/间距档位分布、z-index 散布、rgba 白硬编码、U+FFFD 乱码、magic calc、!important 数**。这些数字是最快暴露"样式堆叠失控"的证据。

## 执行顺序（六步）

### Step 0 — 定标与先验（debug-and-refactor 主刀）

1. 确认审查对象（目录/模块）、主题范围（**浅色+深色都要过**）、是否含逻辑层。
2. **D1 先验**：运行中的产物 = 源码最新构建吗？（产物资源指纹/构建号对比 dist；漂移则先重构建，否则审查结论全空转）
3. 声明审查基线：基线代码的 commit hash 进报告。

### Step 1 — 侦察（cartographer 主刀）

主入口、组件清单、CSS 文件结构、路由/API 面，入台账。大文件记行数与分段，别全文精读——侦察只画骨架。

### Step 2 — 设计工艺审查（成员 3/4/5/6，机械统计先行）

> **常被漏的审查面**（不在组件清单里，但每次都要问）：
> **拖拽与放置** · 触摸/手势（长按、滑动、缩放）· **键盘路径** · 剪贴板（复制/粘贴）·
> 编辑器/画布（框选、平移、缩放）· **图表交互**（图例、下钻、tooltip）·
> **国际化文案**（中英长度差导致的截断与换行）· **状态作用域**（多标签/多弹窗是否串台）


> **一致性判定基准**用 `frontend-ui-consistency`（规范 + 脚本）。注意立场：
> **数值本身没有绝对标准，同一个程序内跨页面一致才是标准**——所以判定用它的「众数判定 + 长尾离群 + 跨文件分歧」，
> 不要拿任何写死的白名单去比对：
> ```bash
> python skills/frontend-ui-consistency/scripts/audit_ui_consistency.py --root <前端源码> --out ui-audit.md
> ```
> 报告的**「跨文件分歧」一节最该看**：它直接对应"A 页面一个尺寸、B 页面另一个尺寸"。

先跑 Step-0 列的机械统计，再按命中项深入。每条发现要落到**选择器/文件:行号/现值**。专查：堆叠失控（版本化 CSS、!important 互相压制）、语义色缺失（硬编码白/语义 hex 不随主题）、刻度失控（字号/圆角/间距各多少种）、布局陷阱（magic calc、可收缩性、溢出防护链）。

### Step 3 — 闭环映射（cartographer 主刀）

- 前端 api 层导出函数 × 全仓调用者 → **0 调用者 = 孤儿**（半暴露功能：后端有、前端没入口）。
- 后端路由表 × 前端调用路径 → 🕳️ 未暴露 / 🪝 悬空调用（调了不存在的端点=接线即 404 的地雷）。
- 双向映射结果必须逐条给出证据（文件:行号）。

### Step 3·5 — 交互点可达性与逃生动作核验（debug-and-refactor 主刀 · Part E 的 E13）

**这一步专治「功能在，但碰不到」**——前四步都只看"有没有、对不对"，没有一步看"在边界状态下够不够得着"，
所以这一步必须独立存在，不能并进 Step 2/3。

1. **工具先行**：`python skills/debug-and-refactor/scripts/audit_escape_entries.py --root <前端源码目录> --out escape-report.md`
   —— 列出「清除 / 取消 / 返回 / 刷新 / 重置」这些**逃生动作**的全部入口 + 每个入口的性质（常驻候选 / 门控 / 菜单型）。
2. **逐入口 × 逐状态**填矩阵：**零行·空结果 / 查询出错 / 门控未开·默认折叠 / 超宽超长**；
   每格三问：**在 DOM 里吗？够得着吗？动作还成立吗？**
3. **判结论**：任何逃生动作名下**只有 门控 / 菜单型 入口** = 边界态下可能整族不可达 → 必须补一个**常驻入口**。
4. **必须跑运行时**：这一步**禁止只做静态推断**——前后端链路静态通还照样可以点不到，
   必须在浏览器里把四个状态各构造一次（筛到零行 / 传错参数让查询失败 / 什么都不做保持默认折叠 / 选列数最多的宽表）。
   **不许用未经验证的「环境不可用」当借口跳过**：若你要声明"实例连不上库 / 没有数据 / 无法构造状态"，**必须附实测命令与输出**（如 `curl -X POST .../query -d '{"sql":"SELECT 1"}'` 的真实返回）。实证：2026-09-18 两轮审查**都**用"隔离实例连不上数据库"为由跳过浏览器实测，而实测 `SELECT 1` **3ms 成功返回** —— 借口是假的，代价是整条可达性结论只能算静态推断。

⚠️ **两条纪律**：① **禁止只验证 E13 举的例子**（曾有人只查"超宽"子情形就写下"E13 ✅ 健康"，而同一模块"零行→清除筛选无入口"原样躺着）；
② 判定单位是**具体动作**不是关键词族（`清除筛选` ≠ `清空表`）。

### Step 4 — UX/无障碍 + 反 AI 味（成员 7/8）

ui-ux-pro-max 按优先级表逐档过（P1 无障碍最重）；hallmark 过 gates。**浅色主题单独核一遍对比度**（次要文字色 × 白底的比值要算出来，别目测）。

### Step 5 — 逐条核验，出清单（铁律）

**报告里的每一条声明，动手前必须逐条核实到证据**——引用的行号、色值、选择器名要精确命中；"未确认/可能"的表述必须当场确认或降级；核验中发现的偏差（多报/漏报/比报告更严重）如实标注。然后按 P0（必修，有实际冲突或功能断裂）/ P1（应修，机械批量）/ P2（可优化）分级，**保留项也列出**（做得好的写清楚，防止修复时误伤）。落地顺序：同批改动合并、逻辑改动独立提交。

### Step 6 — 修复与回归

修复按分级执行；**完成后回归**：逐条复跑 Step 2 的机械统计（档位数/重复数/硬编码数应归零或达标）+ 构建验证（tsc/build/go）+ D1 再验（运行产物=新构建）。回归结果写进提交信息。

## 报告模板

```
结论（三句话内：骨架健康度 / 主要问题集中区 / 总修复量）
P0（必修）每条：症状 → 证据(文件:行号,现值) → 建议
P1 / P2 同上
交互点可达性（E13，必填）：逃生动作 × 四状态矩阵 + 常驻入口结论 + 未填的 ? 全部进缺口段
✅ 保留项（防误伤）
落地顺序（同批/机械/逻辑独立/随修）
```

## 两条血泪纪律

- **审查报告 ≠ 事实**。曾有一份报告 15 条中 1 条不成立（声称"未确认自动翻转"的代码其实已实现）、多处比报告更严重（乱码 24 处 vs 报告的 8 处）——逐条核验是 Step 5 的铁律，不是可选项。
- **D1 不验，审查白做**。审查的是源码，用户看到的是运行产物——两者漂移时，"修好了没生效"的投诉会全部归因到审查结论头上。先验产物，再开审。
